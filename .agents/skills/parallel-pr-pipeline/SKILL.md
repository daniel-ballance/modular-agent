# Work on issues in parallel

1. Read [AGENTS.md](../../../AGENTS.md) and [CONTRIBUTING.md](../../../CONTRIBUTING.md). Read the open issue list and each candidate issue, and check `df -h /` before launching a heavy parallel wave. Run `git fetch origin main` before creating branches or starting subagents in worktrees. Check that a supplied worktree for independent work starts at the fetched `origin/main`. For stacked work, use its parent branch as the base.
2. List every file each issue is expected to touch, including specifications, fixtures and shared checks. Compare every pair of lists and the files in every open pull request. Start issues in the same wave only when their lists are fully disjoint. Sequence overlapping issues or stack a dependent change. Recheck the overlap before expanding a change beyond its list.
3. Give each issue one owner, branch, worktree and pull request. Move its Project Status to In progress when the branch exists. Fix the lowest affected layer first. Work from Layer 1 (specification) through Layer 2 (SDK specification), Layer 3 (SDKs) and Layer 4 (reference implementations) as the change requires. Carry fixes through the affected checks and both languages. Keep global `ma` installs in the permanent `main` checkout.
4. Run the checks in [Checking a change](../../../CONTRIBUTING.md#checking-a-change). When a baselined file shrinks, lower its entry in `scripts/maintainability-baseline.json` before opening or updating the pull request. Keep `WIP` and closing keywords out of commit messages. Use every section of the [pull request template](../../../.github/pull_request_template.md) (`Why`, `What changed`, `Scope`, `Blast radius`, `Checks`, `Agent check`, `Closes #N`) with the full `scripts/check.sh` summary table, or the docs-only command table when those checks apply. Delete your scratch subfolder under `~/.cache/ma-std-tmp/` and remove `rust/target` in any temporary or isolated worktree before reporting. Move the issue to In review when the pull request is open.
5. Have a reviewer who did not write the change run `node scripts/docs-review.mjs` on the committed head, with `--base PARENT_BRANCH` for a stack, and review the change. Use another model family when available. The verdict gives the head SHA, the number of candidates judged and any stale status or untracked work the reviewer found. Apply the review and landing rules in [How work is tracked](../../../CONTRIBUTING.md#how-work-is-tracked) after each push.
6. Leave landing to the operator. The operator checks that the passing verdict covers the exact head sent to `gh pr merge N --squash --match-head-commit SHA` or to the REST squash merge with `sha=`. On a GraphQL rate limit, use the [REST commands](../../../CONTRIBUTING.md#working-in-parallel) for pull request reads, verdict comments, issue edits and the SHA-guarded merge.
7. After every wave of real `ma` runs (or roughly every 5–10 sessions outside waves), use another harness or model to run the [ma-meta-analysis skill](../ma-meta-analysis/SKILL.md) read-only. Audit caching, token burn, compaction, tool and `codemode` behavior, and failures; file reproducible findings as issues. Follow [Evaluating ma on real work](../../../CONTRIBUTING.md#evaluating-ma-on-real-work) for trace setup. Keep this cadence until the operator turns it off.
