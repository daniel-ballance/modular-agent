# AG-UI binding: `modular-agent-agui/1`

This binding, accepted in [ADR 0033](../adr/0033-interface-tools-and-ag-ui.md) and implemented by all four SDKs and `ma`, serves an agent to an application over [AG-UI 1.0 HTTP + SSE](https://docs.ag-ui.com/spec/1.0/basic/transports/http-sse). A thread is a session. A run follows one turn or delivers answers or results that continue one. AG-UI's wire rules apply; this page defines which operations this agent offers. See [ADR 0033](../adr/0033-interface-tools-and-ag-ui.md) and the [upstream research](../research/ag-ui.md).

## Listener and authentication

The routes below share the agent service listener with ACP's WebSocket upgrade when both are enabled. HTTP does not carry the ACP handshake. Authenticate every request before resolving a thread, composing a project, accepting a trace parent or allocating a stream. Apply [WebSocket Connecting](websocket.md#connecting) and [An agent service](websocket.md#an-agent-service) for TLS, server verification, owner-only bearer token files, constant-time comparison, actor binding, project and tenant scope and rights ceilings. Use `https:` off loopback and refuse cleartext there. Use no cookies, URL credentials or body identity claims. This profile requires the bearer token even when the listener uses TLS client authentication. Cross-origin browser requests require an explicit operator origin allowlist; the default is same-origin only. Origin is not identity. A CORS preflight MAY receive a content-free response for an allowed origin without a token. It MUST NOT resolve a session or start work.

A token configuration also names a stable, nonsecret client ID. It identifies the client for history reconciliation and the executor route for Interface tools. Token rotation can retain that ID only for the same principal and scope. Different clients of one actor should have different IDs. A second connection is independently authenticated; a running or previously delivered call does not transfer to it. For this binding the direct actor is always the work actor; `represents` is not used.

| Method and path | Operation |
|---|---|
| `GET /agui/v1` | Returns `{ binding: "modular-agent-agui/1", protocolVersion: "1.0", declaration }` for the authenticated client. |
| `POST /agui/v1/threads` | Takes `{}`. Creates a provisional session and returns HTTP 201 with `{ threadId, declaration }`. The operator chooses the project and tenant for this route. Requires `input` and `watch`. No client-supplied project, tenant, MCP servers or settings. |
| `GET /agui/v1/threads/{threadId}` | Opens or follows an authorized session with `watch`. Returns `{ threadId, declaration, messages, cursor, waiting }`, a fresh snapshot and current wait status. Use this to reconnect. |
| `GET /agui/v1/threads/{threadId}/presence` | Opens an optional, single presence stream per client and session with `watch`. Returns `text/event-stream` with SSE comments only, not AG-UI events. The client keeps it open to answer in-turn interrupts. The server MUST clear presence on loss or loss of scope; it sends a comment at least every 15 seconds. This route confers no rights. |
| `POST /agui/v1/run` | Takes one `RunAgentInput` and returns an AG-UI SSE stream. Requires `watch` and the rights for each requested operation. |

The server MUST apply the [session connection rules](../contracts.md#authority) to every attachment. A run stream marks its client present while connected. For in-turn questions the separate presence stream must already be open. Do not transfer an in-turn answerable view to a replacement presence stream. A snapshot request does not mark presence. Presence is keyed by authenticated client and session, not merely by actor or TCP connection. Opening a new presence stream does not let a different client reuse a question view. A stream close only detaches. This binding does not offer session close, cancellation, steering, rewind, administration or erasure methods. Other Interfaces may perform those operations on the same session.

## Framing and versions

Use UTF-8 JSON POSTs (`Content-Type: application/json`), and SSE replies (`Content-Type: text/event-stream`). Write one complete JSON object per `data: ` line followed by LF LF. SSE comments are allowed. Do not set an SSE `id` or use `Last-Event-ID`. The server MUST bound each JSON request, snapshot reply and encoded SSE event to 64 MiB in its own encoding, and apply [Shared data](data.md#general-rules) for UTF-8, depth and duplicate members. Do not cache responses or let an intermediary buffer streams. Apply normal server and follower resource bounds.

The `/agui/v1` path and discovery response establish the Modular Agent binding. `protocolVersion` in `RunAgentInput` and `RUN_STARTED` declares each side's AG-UI version. The server sends `"1.0"`; it accepts newer 1.x minors and unparseable version strings with a warning, as required by [AG-UI versioning](https://docs.ag-ui.com/spec/1.0/basic/versioning). This profile requires an explicit input version. It does not promise compatibility with unversioned peers. It does not offer the optional Protobuf response. It MUST strip unknown fields in closed input shapes before use. It MUST reject malformed known values and leave open extension data inert except as specified here. Warnings name the field or event type, not its value.

## Run input

| `RunAgentInput` member | Harness operation |
|---|---|
| `threadId` | Open the named session under the authenticated scope. Never creates a session. |
| `runId` | Echo on run boundaries. Require a fresh ID per exchange except a retry. For new input use an unambiguous `agui:` key derived from client ID and run ID, scoped per the [input key rules](data.md#general-rules). A duplicate cannot start work. |
| `protocolVersion` | Check before any operation. |
| `messages` | Reconcile the supplied copy. Admit at most one new user message with timing `now`, or report the listed Interface results. Known messages are comparisons, not admissions. |
| `resume` | Answer the questions on the previous interrupt, not tool calls. See [Interrupts and frontend tools](#interrupts-and-frontend-tools). |
| `tools` | Advertise only this client's registered Interface tools, for this request. Omitted or empty advertises none. The exact registered name, description and parameters MUST match by shared JSON equality (omitted parameters are the empty schema `{}`). Refuse unknown, duplicate, or mismatched offers. Client fields cannot set hints or register a source. |
| `context` | Not used by this profile. Warn if nonempty. The application may supply grounding in the new user message. |
| `state` | At most a copy for the state plugin, never a Harness mutation. See [Shared state](#shared-state). |
| `forwardedProps`, `parentRunId` | No operation. Do not echo or use them to select a parent, scope, configuration or trace. |

A run request carries one new user message, or a set of results and/or question answers. It MUST NOT combine new user input with either. Reject an empty operation. Validate the whole request, history and coverage before the first mutation. Commit individual answers and results using their core first-valid-decision rules. There is no cross-result transaction. If a retry names a decision already committed, return `conflict` and require a refreshed snapshot. The client may then submit only the remaining open decisions. Do not retain raw reports to compare retries. A current accepted report is not new model input. Project a user string or text parts to shared text and inline image data to shared image content. Skip other input media with a warning; do not fetch a URL or resolve a Provider file handle. A tool report whose parts are all skipped still has a result, with empty text for success or a fixed failure description for failure.

## History reconciliation

The record wins. The adapter MUST build messages from current authorized branch entries, not the client's copy or the Runtime's compacted model view. Use server-assigned stable `ma:` IDs derived from the user input ID, the assistant step ID or the terminal result's call ID, with a distinct prefix within that namespace for each role. Live framing and snapshots use the same generated IDs. For new input and result reports the client's message IDs are provisional and MUST NOT use the `ma:` namespace. A committed snapshot replaces provisional messages with their server IDs. A client cannot claim a known or erased server ID for new work.

A snapshot cursor identifies the latest complete snapshot offered to an authenticated client for a thread. Echoing it acknowledges the view the client received; a successful socket write alone does not establish receipt. A newer snapshot supersedes the older cursor for that client. The server returns it with the last committed message ID (or null) in `CUSTOM` named `modular-agent.history`, after each `MESSAGES_SNAPSHOT`; the snapshot HTTP reply carries the same cursor. A client MAY send `MA-History-Cursor` with its next run. Without one, the server validates the supplied history against the latest complete snapshot it offered that authenticated client for the thread, so a stock AG-UI client works for ordinary conversations. A client that missed that snapshot gets `conflict` and reloads. The cursor only lets the server tell a missed snapshot from a changed copy; both are refused, and either way only a new suffix is accepted. The server MUST provide the cursor only if it can validate the exact view delivered with it. It MUST NOT keep a cursor live after the paired snapshot is withheld or truncated. It MAY keep bounded metadata and digests instead of message bodies. A cursor does not grant access. Validate that the presented view is still current under scope, erasure and the output gate before using it.

Validate every supplied known message against that gated view, including its role, visible content and order. Compare only fields of the negotiated message schema, by [shared JSON equality](data.md#general-rules). A redaction sent to this client is its expected copy, not a reason to expose the unredacted record. Strip client-only activity and reasoning from the returned copy; neither can be admitted as new input. The supplied known history MUST match the delivered message IDs in order, through the cursor's last message. New messages can only be a suffix beyond that boundary. Only a new user message or a matching tool report in that suffix is actionable. Never ingest client-supplied system, assistant, developer or activity messages or amend stored messages. An earlier invented ID, omitted boundary, changed known copy, branch move, stale projection, erasure or unknown cursor fails with `conflict` or `cursor_expired`. The client replaces its local conversation from the HTTP snapshot before retrying. The upstream SSE snapshot reconciles by ID and does not reorder existing messages. If a user admission or tool result changes content in a snapshot (for example through a transform), the client uses the snapshot's copy on its next request.

## Runs and events

Open with `RUN_STARTED` only after admitting the work or associating the request with its waiting turn or continuation. Waiting for other authorized answers or reports to make a continuation ready is not another turn. Use SSE comments while waiting; if the origin becomes ineligible, end with `RUN_ERROR`. Do not echo the request on it. While queued, follow only the turn that takes this input; do not attach to an unrelated turn. Use one active run exchange per client and session. Serialize selection of an answer or result's continuation with committing it so it cannot finish before a live follower is installed. During recovery or when another Interface already completed the work, use the snapshot route; do not start an unrelated turn to fill a run. Omit `parentRunId` for sequential runs.

Each event is a projection of the intended recipient's gated view. Close every open text, reasoning, tool and step sequence before `RUN_FINISHED`. `RUN_ERROR` can terminate an incomplete sequence. The following table defines the /1 projection. Events with no useful recipient view are omitted. A text start uses `role: "assistant"`; a reasoning message start uses `role: "reasoning"`.

| Agent event or entry | AG-UI projection |
|---|---|
| `turnStart`, or accepted delivery associated with a waiting turn or a continuation | `RUN_STARTED`; send an initial `MESSAGES_SNAPSHOT` for the committed history not already represented by output on this exchange. |
| Step started and ended | `STEP_STARTED` and `STEP_FINISHED` with the step ID as `stepName`. |
| Readable model text; committed `response` | `TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT`, `TEXT_MESSAGE_END` for new text. Use the final response only for text not already streamed. On a new exchange restore prior committed text via `MESSAGES_SNAPSHOT`. |
| Readable model reasoning | If exposed, `REASONING_START`, message start/content/end, then `REASONING_END`. Never send Provider-only data, including encrypted values. |
| Tool requested or input arriving | Display-only `CUSTOM modular-agent.event`; not dispatch. No executable arguments from a draft, refused, or partly streamed call. |
| A server tool's terminal `toolResult` and any progress | Buffer display framing until the result can be sent. Emit `TOOL_CALL_START`, `TOOL_CALL_ARGS`, `TOOL_CALL_END` then `TOOL_CALL_RESULT` as one group for a settled call. Progress can be `CUSTOM modular-agent.event`. If the group cannot be delivered safely, omit it, not just its result. |
| Interface handoff | The same start/args/end triad without a result, to the executing client only, as specified below. Other recipients see display-only views. |
| Later Interface `toolResult` | `MESSAGES_SNAPSHOT` with the committed tool message, not an executable call, a second raw tool result, or a fabricated answer in the opening run. |
| Visible `input` and history entries | `MESSAGES_SNAPSHOT` for committed conversation, including user, assistant and tool messages. Entries without an equivalent may be `CUSTOM modular-agent.entry`. Do not expose private control records. |
| Questions or call waits and closures | `RUN_FINISHED` with an interrupt outcome for answerable questions, or success with `pendingToolCallIds` for frontend-only waits. Closures and non-answerable notices outside an exchange are visible on snapshot or the next eligible exchange, not appended to a closed run. |
| `turnEnd`; interruption or lost writer | `RUN_FINISHED` with `success` and optional gated result value, `cancelled` for cancel or limit, or `RUN_ERROR` for failure or interruption. A completed turn may leave calls open. Use the wait mapping, not a new core outcome. |
| State plugin snapshot or delta | `STATE_SNAPSHOT` or `STATE_DELTA` as below. |
| Other authorized standard events, job or child activity, or plugin events | `CUSTOM modular-agent.event` carrying the gated event. /1 does not claim native activity or subagent event support. |

Use canonical call IDs. For assistant messages use readable text joined in content order and the visible call parts as AG-UI `function` calls. Use the same assistant message ID as `parentMessageId` when that message is visible. Do not include a call part if its dispatch or result cannot be shown safely. `TOOL_CALL_ARGS.delta` contains the JSON object serialized as a string. Map text and inline images, preserving order. AG-UI's `TOOL_CALL_RESULT` event has no `error` field. In snapshots, set the tool message's string `error` to a gated failure description when status is not `completed`; the exact shared status, if authorized, travels in `CUSTOM modular-agent.event`. If output is only representable through an extension, use the extension after authorization and gating, not a new standard field. `modular-agent.event` is `{ type, data }` using the core event name and gated data (or a [shared output event](data.md#output-events) as applicable), and `modular-agent.entry` has the recipient's entry projection. `RAW.event` is only for a gated foreign event a plugin explicitly supplies for pass-through, with a configured `source`. Neither extension is actionable. Never put the only copy of a standard outcome, message, call identity or result in an extension. Do not expose credentials, raw history, Provider-only data, private trace checkpoints or internal executor route metadata in either channel.

Terminal events MAY report usage grouped by Provider and model for work in that run only. Map total input to `input + cacheRead + cacheWrite`, output to `output`, and report available cache subdivisions. Do not attribute a previous segment's usage to a continuation. Omit usage if it cannot be attributed to the exchange. Replay does not add usage.

## Interrupts and frontend tools

**Questions.** A `RUN_FINISHED` interrupt closes the AG-UI run, not necessarily the turn. For an eligible question use its request ID for `id`, its kind for `reason`, its gated prompt for `message`, and its expiry as an ISO 8601 `expiresAt` only for a deadline that closes the question, not for the end of a `leaveOpen` wait. For approvals include `toolCallId` and an exact unchanged name and arguments in the prompt. Answer schemas are `{ allow: boolean }` for approval, one of the request's strings for choice, and a string for text or link acknowledgment; when supplied on the wire, `responseSchema` is the corresponding JSON Schema object. `resolved` supplies the value and `cancelled` declines. Map `{ allow: true }` to the core `allow` value and `{ allow: false }` to decline. Link questions include their gated URI as `metadata["modular-agent.link"]`; the acknowledgment is not proof of sign-in. Do not accept secrets through this binding; use a separate eligible route. This binding does not define a credential activation relay.

The presence stream is optional. A client without one, such as a stock AG-UI client, is never offered an answerable approval on this route; the core rule refuses the approval unless another eligible Interface is present. Interface-run tools do not need presence: they wait with a deadline. For an in-turn wait, require the client's independently open presence stream before offering an answerable interrupt. The next run POST MUST act on that same presence route to answer while the turn remains open. The server MUST use the existing approval and question operations, including exact unredacted route delivery, eligibility, deadlines and first committed answer. Losing presence revokes approval eligibility on that route; the core refusal applies if no other eligible route remains. Do not extend an approval past a turn. If no eligible AG-UI route can take an approval, the turn can wait on another eligible Interface, otherwise the core refuses the approval. Non-approval questions already left open may be answered on reconnect under the core late-answer rules without a presence stream. The adapter MUST reject missing coverage for its still-answerable delivered interrupts, and MUST NOT infer a decline from omission. Ignore unknown interrupt IDs with a warning, without treating them as answers. If a delivered question closed elsewhere, it cannot be answered again. Its current status is available on snapshot. Never show an unanswerable view as an actionable interrupt.

**Frontend tools.** Only a committed Interface handoff may produce the unanswered call triad. Use the actual gated dispatch input, including any `tool.before` changes, not the model's draft. The opening run MUST NOT emit `TOOL_CALL_RESULT` for a frontend call. After a successful `RUN_FINISHED`, the client can execute or decline only the calls named in `pendingToolCallIds`, in call order. Buffered output, drafts and live progress are never executable. For mixed runs with a question interrupt, the client instead derives the list from unanswered handoff triads in that run; closed server tools always have results in that stream. The client MUST NOT act on an error, a cancelled or truncated run, or any snapshot or replay. Resolve all the waits of the run before continuing the thread. A reply is a new `role: "tool"` message with the canonical `toolCallId`, content and an optional string `error` for failure or decline. It is not a `resume` entry. Map presence of `error` to `failed`, otherwise to `completed`. Use the error text as a text part if there is no other failure description. /1 has no standard structured result field for a frontend tool; do not offer definitions that require a structured `value` on completion. Ignore message metadata for authority, provenance and result status.

The HTTP adapter stages the executable handoff after `toolStarted` and holds it until a qualifying terminal group can be sent after the originating `turnEnd`. An in-turn interrupt does not release the staged tool; the later exchange for that turn can release it once, on the original client route. Do not put an outstanding handoff's executable input in a snapshot. No incomplete handoff may be inferred from historical assistant calls. It MUST gate the entire group for the recipient and repeat the final authority, route, deadline, writer and erasure checks at release. It MUST NOT send a success terminal authorizing a subset inferred from a truncated group. If the group becomes unsafe before release, withhold it and use `RUN_ERROR`; the Harness settles the call if it can confirm non-delivery, otherwise it remains open until its deadline. Client loss after release does not prove execution or non-execution. The Harness does not repeat a handoff, even when the client reports it missed the run.

## Shared state

A configured plugin owns the document. Subscribe to its `modular-agent.agui.stateSnapshot` events with `{ revisionId, snapshot }` and its `modular-agent.agui.stateDelta` events with `{ baseRevisionId, revisionId, delta }`. Revision IDs are opaque strings. The operator selects the plugin; events of the same name from another plugin are not state. Gate these events before projection. The binding serves at most one document per session. An input `state` is a client's copy, not an update. The adapter starts each run with the plugin's current snapshot if the plugin is present. It MUST project a gated delta only when its base is the revision last sent unchanged to that recipient. Deltas use RFC 6902. If the base is stale or a gate blocks or changes a patch, suppress it. Send a fresh gated snapshot before any further delta; do not use a redacted snapshot as an unredacted patch base. If the snapshot is withheld, suppress state output. No plugin means no state events. The Harness does not merge, persist or authorize a shared document as a new kind of state. Plugins remain responsible for their controlled copies and erasure.

## Output gate, errors and reconnect

Check `watch`, scope and [pending erasure](../contracts.md#cross-session-coordination) at delivery, including after a buffered wait. Gate exact recipient views before projecting events and recheck the outgoing shape and size. Gate initial and final snapshots, errors, declarations, state, custom data and replay. Omit withheld display items and their dependent frames. Do not reopen a withheld stream through a snapshot or extension. If a required end, question or actionable view cannot be delivered, use a content-free error when needed to keep the stream valid. Held streams use [the shared rules](data.md#output-events) and [remote gate limits](plugin.md#held-output). Never store redactions as agent history.

Before streaming, return a JSON error `{ code: string }`: 400 `invalid_request` for malformed data or version (`not_supported` for an unsupported major), 401 `unauthenticated`, 404 `not_found` for inaccessible or missing sessions, 403 `refused` for an operation denied within an accessible session, 409 `conflict` for stale history, stale waits or duplicate work, 409 `cursor_expired` for unavailable reconciliation metadata, 413 `result_too_large` for a size refusal, or 503 `busy` or `unavailable` for a capacity or writer failure. A withheld HTTP reply uses 403 `output_withheld`. After streaming begins send `RUN_ERROR` with a bounded code and fixed message if content is withheld. No error may disclose an unauthorized ID, arguments, output or credentials.

Reconnect with a fresh authenticated request, not an SSE offset. The snapshot route returns the current gated branch from a single committed watermark. `waiting` lists current eligible questions and open Interface calls for this client as `{ questions: Interrupt[], toolCalls: [{ toolCallId, expiresAt }] }`. Tool expiry is ISO 8601. The HTTP snapshot also returns `lastMessageId` (or null). It supplies status and answer routing, not an authorization to execute. Do not replay handoff arguments in this view for a pending Interface call. Approval views require their live exact route and are not renewed by a snapshot request alone. A client that already executed may submit the result on its original authorized route using a fresh snapshot after reconnect, even after restart. A client that never saw a qualifying terminal group MUST NOT execute from a snapshot; it can wait for expiry. If the server cannot tell whether that group was received, a valid report on the authorized route is still an assertion from that executor, not proof that the client ran the tool. Delivery and cursor metadata may expire or be lost on restart. The record, result deadlines and input keys are authoritative. Do not reconstruct missed chunks, claim the client saw an earlier delivery, cancel on EOF or replay effects. A duplicate new input run returns `conflict` and the client refreshes; it never creates a second input. The server MUST refresh history at a single watermark at run end (send a final `MESSAGES_SNAPSHOT` and its cursor before the terminal event if it can disclose them).

For example, an approved browser tool can be left open by turn `t1`. Run `r1` finishes with that call in `pendingToolCallIds`. A new authenticated connection of the same client sends the result in `r2`. The Harness records it against `t1`; `r2` follows the continuation `t2`. If the browser disappears before reporting, `t1`'s deadline settles the call instead. Neither path starts the tool again.

## Trace context

Use [the telemetry profile](../telemetry.md#context-on-the-wire). Extract W3C HTTP `traceparent` and operator-allowed `tracestate` per authenticated work request and only from a trusted peer. No baggage. A starting input carries its context even if queued. A question answer in a live turn or a result report does not reparent that existing turn; a later continuation has its own operation context and can link to its origin. Use the stored parent for crash recovery. A presence stream, snapshot read or connection upgrade does not determine a turn's trace. SSE responses carry no W3C context fields; do not put context in AG-UI metadata, `CUSTOM`, `RAW`, history projections, errors or tokens.
