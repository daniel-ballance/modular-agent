# Research: Grok with The X Subscription

Checked 2026-11-22. **Outcome:** [ADR 0031](../adr/0031-subscription-providers.md) keeps the existing device sign-in for `grok()`, after a real account confirmed that requests made this way draw on the plan.

Can the four SDKs sign a person in with their own X Subscription, SuperGrok, or X Premium and call Grok against that plan, as Grok Build does?

**Answer:** Grok Build supports browser and device sign-in. The old `ma` device request still starts a login and now sends the person to `accounts.x.ai`. That is not evidence of a new OAuth issuer, or proof that a freshly migrated account can finish sign-in and use its included credits through `ma`. Grok Build's subscription inference proxy is not the public API host that `ma` uses. There is no documented third-party subscription OAuth registration or raw model API contract in the sources checked. Do not ship the first-party client ID as an SDK default on the strength of this research.

## What the first-party sources show

- [The October 12 announcement](https://x.ai/news/x-subscription) and the [subscription overview](https://docs.x.ai/x-subscription/overview.md) describe a shared usage pool and an optional move from existing plans. [Sign-in](https://docs.x.ai/x-subscription/sign-in.md) says the shared page authenticates the person; it does not link accounts or switch plans. The [domain notice](https://docs.x.ai/x-subscription/sign-in-domains.md) specifically describes Cursor's October 30 move and lists `auth.x.ai` separately from `accounts.x.ai` and `accounts.spacex.ai`. The [X Premium migration page](https://docs.x.ai/x-subscription/x-premium.md) describes X benefits and checkout, not SDK model entitlements.
- The [Build overview](https://docs.x.ai/build/overview.md), [CLI reference](https://docs.x.ai/build/cli/reference.md), and [authentication and network guide](https://docs.x.ai/build/enterprise.md#authentication) describe default browser OIDC, `grok login --device-auth` for remote terminals, and refresh for both. The last guide identifies `auth.x.ai` for OAuth/OIDC and `cli-chat-proxy.grok.com` for inference. `grok logout` is documented to clear cached credentials; that does not establish remote revocation.
- The [official installer](https://x.ai/cli/install.sh), read as text, names [the stable version pointer](https://x.ai/cli/stable) and a [public Google Cloud Storage fallback](https://storage.googleapis.com/grok-build-public-artifacts/cli/stable). Stable was **Grok Build 1.0.92**. I downloaded the [Linux x86-64 artifact](https://x.ai/cli/grok-1.0.92-linux-x86_64.zst) into a new empty directory under `$HOME/.cache/ma-std-tmp/grok-research/`, decompressed it, and read its strings and bundled help text. The compressed file's SHA-256 was `af6423d41f3216536c7ca11cc4bb0c3841aeff16e706e92a9e9cee8486acb9f4`. I did not run the installer or binary or read any local credentials. The installer names `https://auth.x.ai::b1a00492-073a-47ea-816f-4c329264a828` as its OIDC credential lookup key and `https://accounts.x.ai/sign-in` as the legacy key. That ties the UUID to first-party tooling; it is not a public SDK registration. I did not recover an independently verified complete set of compiled consumer defaults for client ID, scopes, or referrer.

## Endpoints and parameters

“Form POST” below means `Content-Type: application/x-www-form-urlencoded`.

| Step | Address and parameters | Evidence and limits |
|---|---|---|
| Discover | `GET https://auth.x.ai/.well-known/openid-configuration` | [Live discovery](https://auth.x.ai/.well-known/openid-configuration) returned 200, issuer `https://auth.x.ai`, S256, authorization-code, refresh, and device grants, and `none` among the token endpoint client authentication methods. Both well-known paths checked on `accounts.x.ai` returned 404; on `accounts.spacex.ai` they returned 403. These are front-end sign-in hosts for this purpose, not replacement issuer URLs. This does not establish whether the services share internal servers. |
| Browser | `GET https://auth.x.ai/oauth2/authorize`; `response_type=code`, `client_id`, `redirect_uri`, `scope`, `code_challenge`, `code_challenge_method=S256`, `state`, `nonce`. Exchange at the token endpoint with `grant_type=authorization_code`, `client_id`, `code`, `code_verifier`, and the same `redirect_uri`. | The binary has the authorize URL template, `http://127.0.0.1:<port>/callback`, state validation, and the prompt “Paste the URL here if it doesn't connect:”. Its bundled OIDC text describes an ephemeral port. Paste is a way to deliver the redirect, not a separate out-of-band grant. The third-party extension below defaults to port 56122; that is not an xAI-documented requirement. One unauthenticated authorize request using that redirect returned 403, so accepted redirects and the browser handoff were not verified. |
| Device start | Form POST `https://auth.x.ai/oauth2/device/code`. The exact `ma` form is `client_id=b1a00492-073a-47ea-816f-4c329264a828`, `scope=openid profile email offline_access grok-cli:access api:access`, `referrer=modular-agent` (default label). | The probe returned HTTP 200, `expires_in=1800` seconds and `interval=5` seconds. Both `verification_uri` and `verification_uri_complete` pointed to `https://accounts.x.ai/oauth2/device`. I discarded the codes and did not visit the page or poll. The binary also contains `x-grok-client-version`, `x-grok-client-surface`, and `grok-build` in its device-flow code; the exact `ma` request succeeded without either header. The necessity of `referrer` was not tested. |
| Device poll | Form POST `https://auth.x.ai/oauth2/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `client_id`, and `device_code`. | Discovery, binary strings, and current clients agree. Honor the advertised deadline and interval; continue on `authorization_pending`, add five seconds on `slow_down`, and stop on refusal, expiry, or cancellation. The 1,800 seconds is the **device-code** lifetime. |
| Refresh | Form POST `https://auth.x.ai/oauth2/token` with `grant_type=refresh_token`, `client_id`, and `refresh_token` for the registration that obtained the token. | Build docs say browser and device credentials refresh. The binary has token expiry, proactive refresh, and refresh rotation handling. Use returned `expires_in`, refresh before expiry, store a replacement refresh token atomically, and keep the prior one if none is returned. Actual access-token and refresh-token lifetimes were not verified. Pi and `ma` use one hour if access expiry is missing, with a five-minute margin; that is a client fallback, not an xAI guarantee. The binary's old proxy example mentions seven days for a legacy stored token, not for current OIDC tokens. |
| Revoke | `POST https://auth.x.ai/oauth2/revoke`, advertised by discovery. | Not called. Client-specific behavior and whether Build calls it on logout are unverified. |
| Build inference | Base `https://cli-chat-proxy.grok.com/v1`. The binary's bundled example uses `POST /v1/chat/completions` with `Content-Type: application/json`, `Authorization: Bearer <session token>`, `X-XAI-Token-Auth: xai-grok-cli`, and `x-grok-model-override: <model>` (documented there as optional for its `grok-build` default route). | The example uses a legacy stored token. Other binary strings show Responses and Chat Completions backends, plus `x-grok-client-version`, `x-grok-client-identifier` (`grok-shell`), `x-grok-client-mode`, and conversation headers. This does not tell us which inference path every current model uses or which other headers are required. No inference requests were made. |
| Build catalog | `grok models`; Build also refreshes model metadata from the proxy. `GET https://cli-chat-proxy.grok.com/v1/models` returned 401 without credentials. | CLI docs and binary strings link the catalog to the proxy; the unauthenticated response confirms a protected route, not its schema, required headers, or model entitlements. |
| Public inference and catalog | `POST https://api.x.ai/v1/responses`, `Authorization: Bearer <API key>`, `Content-Type: application/json`; for streaming, use `stream: true` and read SSE. `GET https://api.x.ai/v1/models` (or `/v1/language-models` for richer language model metadata) with the same bearer key. | [Responses](https://docs.x.ai/developers/rest-api-reference/inference/responses.md), [model listing](https://docs.x.ai/developers/rest-api-reference/inference/models.md) and the [Grok 4.7 example](https://docs.x.ai/developers/grok-4-7.md) document API-key use, not subscription bearer use. `/v1/models` returned 401 without credentials. No Build identity or OAuth referrer is documented for these API requests. |

## What changed from `ma`

[`ma`'s OAuth code](https://github.com/daniel-ballance/modular-agent/blob/b21bf624/rust/crates/provider-responses/src/oauth.rs) uses the exact device form above, based on [Pi `pi-ai` 1.5.2](https://www.npmjs.com/package/@earendil-works/pi-ai/v/1.5.2). The [configuration reference](../reference/standard-configuration.md#providers) calls out `referrer` as a name, not a credential. The [inference adapter](https://github.com/daniel-ballance/modular-agent/blob/b21bf624/rust/crates/provider-responses/src/lib.rs) sends the token to `https://api.x.ai/v1/responses` as a bearer, with JSON and `Accept: text/event-stream`; it does not send Build's proxy headers. The user's account is reported still working. The independent probe shows that this client ID and scope still **start** the flow under the shared UI, not that redemption, refresh, inference, or usage accounting work on every migrated or legacy plan. Do not change the issuer or token endpoint to match the browser's address bar.

For comparison only:

- [Pi `@earendil-works/pi-ai` 1.6.0 on npm](https://www.npmjs.com/package/@earendil-works/pi-ai/v/1.6.0), the latest seen, still has the same UUID, scope, device flow and public Responses host, with `referrer=pi`. Its `dist/providers/data/xai.json` bundles `grok-4.3`, `grok-4.5`, `grok-4.6` and `grok-4.7`, the same IDs as [the current `ma` catalog](https://github.com/daniel-ballance/modular-agent/blob/b21bf624/rust/crates/provider-responses/src/models.json). Neither static catalog is an entitlement list.
- [`kenryu42/pi-grok-cli` 0.9.4 at `3f5837a`](https://github.com/kenryu42/pi-grok-cli/tree/3f5837aac6d0275d86d983b96be90bfecb0d0c4a) uses the same default UUID and scope, browser PKCE with loopback or manual paste as well as device login, and the Build proxy with Responses streaming. Its `src/provider/stream.ts` supplies the Build token-auth discriminator, model override, and official-looking identifier, version and User-Agent. It reports that a stale or missing client version can yield HTTP 426. Its `src/models/catalog.ts` bundles a wider list, including `grok-build` and `grok-4.7-build-fast`; the README explicitly says the list is not live. This is evidence of what a third party implements, not evidence of permission, minimum headers, or a stable contract. Do not copy its version or User-Agent impersonation.

## Models and billing

The [Grok 4.7 guide](https://docs.x.ai/developers/grok-4-7.md) calls `grok-4.7` the Build default and says Grok 4.7 Fast is available in Build and Cursor, billed through the plan there, excluded from Build's free tier, and unavailable on the public API. The binary's bundled help shows `grok-4.7[fast=true]` as a CLI selector on agents that support it, not a verified HTTP model ID. The `grok-build` ID also appears in the bundled proxy example; its current meaning and availability were not verified. No first-party per-plan raw API model list was found. Use the signed-in Build model list for that account, not Pi's static entries or the developer API's inventory. The [subscription pricing FAQ](https://x.ai/pricing) states: “API usage is billed separately at standard model rates and doesn’t draw from your plan’s usage pool.” Do not silently fall back to an API key or promise subscription billing for the old route.

These are **developer API** limits, not per-plan promises ([model table](https://docs.x.ai/developers/models.md), [Responses reasoning](https://docs.x.ai/developers/model-capabilities/text/reasoning.md)):

| Model | Context | Documented `reasoning.effort` |
|---|---:|---|
| `grok-4.7` | 500,000 | `low`, `medium`, `high` (default), `xhigh`; no off |
| `grok-4.6` | 500,000 | `low`, `medium`, `high` (default), `xhigh`; no off |
| `grok-4.5` | 500,000 | `low`, `medium`, `high` (default); no distinct `xhigh` |
| `grok-4.3` | 1,000,000 | Not specified by that Responses effort table |

## Terms

- [X Subscription Consumer Terms](https://x.ai/legal/x-subscription-terms-of-service), October 27, §2: “You may not share your account credentials or make your account available to anyone else”. §3 includes “reverse engineer, disassemble, decompile, decode, or otherwise attempt to derive or gain access to the source code, object code or underlying structure of the Service” among the prohibitions. The [general Consumer Terms](https://x.ai/legal/terms-of-service) also prohibit account sharing and incorporate the AUP.
- [Acceptable Use Policy](https://x.ai/legal/acceptable-use-policy): “Accessing the Services through unauthorized automated or non-human means, whether through a bot, script, or otherwise”. It also prohibits “circumventing any rate limits or restrictions or protective measures and safety mitigations”.
- [Bundled Subscription Terms](https://x.ai/legal/bundled-subscription-terms), §10: “You may not allow others to use your account to access any Paid Service.” §1 points legacy X Premium billing to the applicable [X purchaser terms](https://legal.x.com/purchaser-terms) until migration.

I found no statement naming `ma` or Pi, no blanket ban on all third-party software, and no permission to distribute raw subscription clients that use Build's registration. The bundled curl example describes direct use of one's own CLI session; it does not document third-party OAuth registration, impersonation, or credential sharing. Device-code issuance proves technical acceptance at one step, not permission or continuing tolerance.

## Recommendation for the SDKs

1. For a **subscription**, use the documented first-party surface if an integration is needed now: let the user run `grok login` (browser) or `grok login --device-auth` (remote), use `grok models` to see their choices, and use [Grok Build over ACP](https://docs.x.ai/build/cli/headless-scripting.md#acp) for an agent integration. Build owns sign-in and its credentials; do not read or import them. ACP runs an agent, so it is not a drop-in implementation of a raw model Provider.
2. For a **raw model Provider** now, ship `grok()` with an explicitly selected API key and separate billing. Use the public Responses URL and headers in the table, recommend `grok-4.7` as the initial coding model (500,000 context; omit effort when unset), and intersect any additional advertised IDs with the API-key inventory and the SDK's documented capability table. Preserve encrypted reasoning items on same-provider follow-ups as the 4.7 guide requires. Ship **no default subscription OAuth client ID, scopes, Build headers, or static subscription model list** in the SDK. If the current `ma` path must be preserved during the move, keep it explicitly labeled as existing compatibility rather than enrolling new SDK users through it by default.
3. Before shipping native subscription support, get written xAI authorization and a registered client ID, allowed scopes and redirects, an approved inference path and header contract, and a way to list entitlements and distinguish included usage from paid usage. Then use browser S256/loopback by default and device flow for remote terminals **if enabled for that registration**. The table gives the endpoints and the exact existing compatibility profile; it is not a new registration. Use an SDK-owned `referrer` if xAI asks for one, never a fabricated Build identity. After approval, verify fresh login, refresh, listing, and a small test request with dedicated X Subscription and legacy test accounts. Check how each request was billed. No authenticated check of any of those steps was made here.

**Offline tests in Rust, Go, Python and TypeScript:** Share request and response fixtures. Mock API-key listing and Responses streaming, auth and entitlement errors, quota versus rate limiting, unknown models, effort mapping, and encrypted reasoning replay. Assert the public and subscription credentials cannot cross hosts or silently fall back to each other. For any retained or approved OAuth path, test exact form fields and referrer placement, trusted HTTPS verification URLs, polling interval/backoff/deadline/cancel, error redaction, early and concurrent refresh, refresh rotation and invalid grants. For approved browser login, test S256, matching state and nonce, exact loopback redirect and port, timeout and pasted callback validation. Use synthetic credentials and a fake clock; no live sign-in is needed for those tests.
