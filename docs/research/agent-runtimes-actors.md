# Agents as actors and durable runtimes

Checked **2026-11-22**. Release status comes from first-party release records or product docs. The findings below use docs, repositories and engineering posts I opened and read. Search results and indexed excerpts were leads, not evidence. I could not verify John Suh’s X post directly. The comparison uses the brief’s account of it, not a quotation. No products were run.

## What has shipped

**Cloudflare Durable Objects.** Generally available since 2021. A named object is an addressable, single-threaded Worker with attached, strongly consistent storage. It wakes on demand and can lose its in-memory state when idle. Hibernating WebSockets can stay connected across eviction. That gives an agent an address and a place for durable state, not automatic recovery of an interrupted loop. The Workers isolate is a compute boundary; it is not a separate sandbox for code called inside the same Worker. [GA post](https://blog.cloudflare.com/durable-objects-ga/) · [Object model](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) · [Workers security model](https://developers.cloudflare.com/workers/reference/security-model/)

**Cloudflare Agents SDK.** Shipped as `agents@0.34.0`. A Durable Object hosts an agent’s lifecycle, state, schedules and connections. The loop is a separate capability in Cloudflare’s terms: its Pi adapter runs Pi Durable on object SQLite and wakes work after eviction. The SDK also offers fibers with recovery callbacks; its generic `Sessions` capability stores chat history and is marked experimental. For agent-written code, Dynamic Workers can load source in a separate isolate with chosen bindings and egress. Facets add isolated SQLite; the SDK repository’s gadget hot-swap design is an experiment, not a general extension lifecycle guarantee. [Release](https://github.com/cloudflare/agents/releases/tag/agents%400.34.0) · [SDK](https://developers.cloudflare.com/agents/) · [Sessions](https://developers.cloudflare.com/agents/runtime/capabilities/sessions/) · [Fibers](https://developers.cloudflare.com/agents/agent-class/durable-execution/) · [Dynamic Workers](https://developers.cloudflare.com/dynamic-workers/) · [Facets](https://developers.cloudflare.com/dynamic-workers/usage/durable-object-facets/) · [Gadgets experiment](https://github.com/cloudflare/agents/blob/main/experimental/gadgets.md)

**Rivet Actors.** Rivet is a general actor platform, not an agent loop. The shipped `v2.3.33` line gives each actor an identity, persistent state, queues and a lifecycle that sleeps and wakes. Rivet’s optional agent library runs Pi Durable on actors. For generated code, Rivet documents a separate [Secure Exec plugin pattern](https://rivet.dev/secure-exec/docs/use-cases/plugin-systems/). Actor storage separation does not by itself confine code loaded into the actor. I found no built-in agent-authored hook install contract in the actor docs. [Release](https://github.com/rivet-dev/rivet/releases/tag/v2.3.33) · [Actor lifecycle](https://rivet.dev/actors/docs/lifecycle/) · [Agent library](https://rivet.dev/agents/docs/quickstart/) · [Secure Exec](https://rivet.dev/secure-exec/docs/)

**Rivet Workflows.** Shipped in RivetKit, not just announced. This TypeScript workflow engine runs inside an actor. It records named step results and replays them instead of rerunning completed steps. It can sleep, wait on the actor’s queue, retry, and join or race branches. Rivet’s example puts model calls and tools in checkpointed steps while the loop and queue determine what runs next. Workflow state has its own storage namespace; workflow code still runs with the actor, not in a sandbox for generated plugins. [Release post and agent example](https://rivet.dev/changelog/2026-02-24-introducing-rivet-workflows/) · [Engine design](https://github.com/rivet-dev/rivet/blob/v2.3.33/rivetkit-typescript/packages/workflow-engine/architecture.md)

**Vercel Eve.** This is Vercel’s open-source TypeScript agent framework, shipped as `eve@1.3.0`. The filesystem is the authoring layout for tools, hooks and channels, not a shared runtime filesystem. Eve uses the Workflow SDK to checkpoint turns and park them on input. After a crash it replays completed steps; an interrupted step can repeat model work and leave tool effects uncertain. Trusted hooks and tool implementations run in the app. Shell work goes to the configured sandbox, such as a Vercel microVM; `just-bash` is a weaker, in-process option. Authored dynamic functions can vary tools per model call. A separate opt-in tool runs model-written JavaScript as a workflow with access only to bounded subagent calls, not ordinary tools, imports or secrets. Neither is a live installer for privileged hooks. [Release](https://github.com/vercel/eve/releases/tag/eve%401.3.0) · [Repository](https://github.com/vercel/eve) · [Execution and recovery](https://eve.dev/docs/concepts/execution-model-and-durability) · [Security](https://eve.dev/docs/concepts/security-model) · [Hooks](https://eve.dev/docs/guides/hooks) · [Dynamic definitions](https://eve.dev/docs/guides/dynamic-capabilities) · [Generated workflow tool](https://eve.dev/docs/tools/workflows#add-a-runtime-generated-workflow-tool)

**Pi CLI and extensions.** The `pi-mono` project now lives at `earendil-works/pi`; `v1.6.0` shipped. The coding CLI’s session file is a JSONL tree. Its resume docs describe reopening and branching history, not recovering an interrupted run from an execution checkpoint. Extensions can add tools, commands and hooks. Pi documents a tool requesting a reload after the agent settles; it cannot reload in the middle of a run. Project code requires trust. Loaded extensions run with the CLI process’s permissions, so reloading code the model wrote does not isolate it. [Release](https://github.com/earendil-works/pi/releases/tag/v1.6.0) · [Sessions](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/sessions.md) · [File format](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/session-format.md) · [Extensions and reload](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/extensions.md)

**Pi Durable.** `@earendil-works/pi-durable` is a shipped package in the same repo, not a name for CLI history. It keeps conversation state and a graph of checkpointed tasks in a storage backend. A started tool with no result reruns only if declared replay-safe; a parked tool can wake on a signal or deadline. The process owns the extension registry. Replacement keeps old code for running calls and resolves new code at the next task phase. That is a lifecycle rule, not confinement. Its separate Code Mode tool runs model-written JavaScript in QuickJS and journals nested tool results for replay. Earendil also publishes a Cloudflare example. [Package and design](https://github.com/earendil-works/pi/tree/v1.6.0/packages/durable) · [Cloudflare example](https://github.com/earendil-works/pi-durable-cloudflare)

**DeepSeek Harness.** A released developer preview (`dsh-v0.2.3-alpha.2`), not GA. Cordis plugins supply in-process services, including the loop, with reversible registrations. Profile configuration controls hot reload. The session log preserves history and can close a crash-orphaned turn as interrupted; that is not continuation of the same turn. Its process sandbox confines spawned commands according to a filesystem policy, not the TypeScript plugins themselves. I found no supported path that installs model-authored hooks into a live session under a separate trust boundary. [Release](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.3-alpha.2) · [Preview README](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.3-alpha.2/README.md) · [Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.3-alpha.2/docs/architecture.md) · [Cordis](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.3-alpha.2/docs/cordis-primer.md) · [Session recovery](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.3-alpha.2/docs/subsystems/session.md) · [Process sandbox](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.3-alpha.2/docs/subsystems/sandbox.md)

**Temporal.** The shipped server (`v1.32.2` checked) orchestrates Workflows on workers. Workflow code must replay deterministically from event history. Model calls and tools can run as Activities, with recorded outcomes steering later branches. The model can choose the next action; it need not choose the same action in a new run. An Activity that made an effect before its completion was recorded may retry. Temporal is not an agent harness or a facility for installing agent-written hooks. The Python Workflow sandbox checks determinism, not safe execution of untrusted code. [Server release](https://github.com/temporalio/temporal/releases/tag/v1.32.2) · [Workflows](https://docs.temporal.io/workflows) · [Activities](https://docs.temporal.io/activities) · [Agent example](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal) · [Python sandbox](https://docs.temporal.io/develop/python/python-sdk-sandbox)

**Cloudflare Workflows.** Generally available since April 2025. Worker code uses `step.do` for retryable work with saved results and can sleep or wait for external events. The rules call for idempotent effects because retry can repeat a step. This is distinct from Durable Object storage and SDK fibers. Cloudflare also documents Dynamic Workflows, where a loader supplies tenant-specific code in a Dynamic Worker. That is a way to run code loaded at runtime, not permission to modify the parent agent. [GA post](https://blog.cloudflare.com/workflows-ga-production-ready-durable-execution/) · [Rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/) · [Dynamic Workflows](https://developers.cloudflare.com/dynamic-workers/usage/dynamic-workflows/)

**Zapier Zaps.** A shipped hosted product. An app event triggers a workflow whose actions are configured in an editor. Code steps can run small Python or JavaScript snippets; Zapier documents a time- and memory-limited sandbox for Python. Zapier can retry failed steps or replay the entire Zap as a new run from its trigger data. This is not deterministic replay of a general program from a saved execution history. The editor is the contrast, not an absence of code or retries. [Triggers](https://help.zapier.com/hc/en-us/articles/8496244568589-How-Zap-triggers-work) · [Code steps](https://help.zapier.com/hc/en-us/articles/8496326417549-Use-Python-code-in-Zap-workflows) · [Replay](https://help.zapier.com/hc/en-us/articles/8496241726989-Replay-Zap-runs)

## What they agree on, and where they differ

One concrete self-editing example is [Ultimate](https://github.com/HazAT/ultimate), a local app built on Pi Durable. Its maintainer docs say the agent can edit its own source, and that server extension files can change tools and hooks without a restart. I did not find a separate confinement guarantee for those hooks. This shows self-editing and reload, not a tenant-safe plugin system. [Reload boundaries](https://github.com/HazAT/ultimate/blob/main/AGENTS.md#layers-and-how-they-reload)

- **State, execution and identity are separate promises.** An object or actor gives work a stable address and a place to wake. A saved transcript gives context. Only execution records tell a loop what to do next. Cloudflare’s Pi adapter layers all three; the Pi CLI’s JSONL is the counterexample to treating saved history as execution recovery. [Cloudflare Pi adapter](https://developers.cloudflare.com/agents/harnesses/pi/) · [Pi file format](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/session-format.md)
- **Deterministic control can surround model decisions.** Temporal replays a Workflow from event history. Rivet puts replay inside an actor. Cloudflare saves named steps, Eve checkpoints loop steps, and Pi Durable resumes task phases. The replay unit matters: a crash after an effect but before its receipt is not evidence the effect failed. [Temporal Activities](https://docs.temporal.io/activities) · [Rivet engine](https://github.com/rivet-dev/rivet/blob/v2.3.33/rivetkit-typescript/packages/workflow-engine/architecture.md) · [Cloudflare rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/) · [Eve crash rules](https://eve.dev/docs/concepts/execution-model-and-durability#resuming-after-a-crash) · [Pi Durable tools](https://github.com/earendil-works/pi/tree/v1.6.0/packages/durable#tools)
- **Changing a tool offer, running a generated program and installing a hook are different operations.** Eve and Cloudflare document bounded execution of generated programs. Pi documents reload of trusted code; Pi Durable swaps registry entries at phase boundaries. None of those facts implies safe, portable handover of arbitrary live hook state. [Eve generated programs](https://eve.dev/docs/tools/workflows#add-a-runtime-generated-workflow-tool) · [Cloudflare Dynamic Workers](https://developers.cloudflare.com/dynamic-workers/) · [Pi reload](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/extensions.md) · [Pi Durable reload](https://github.com/earendil-works/pi/tree/v1.6.0/packages/durable#reload)

## Modular Agent today

- **Runtime is a turn capability, not an actor scheduler.** A session selects at most one. The Harness owns records and authority; the Runtime uses mediated model, tool and hook calls. The SDK can place a Runtime in process, in a child process or at a service. In our vocabulary an [actor](../../GLOSSARY.md#actors-and-authority) is a principal, not a compute instance. [Runtime contract](../contracts.md#harness-and-runtime) · [Plugin wire](../bindings/plugin.md#the-host-asks-the-runtime) · [SDK placement](../sdk/placement.md#the-matrix)
- **Durable is more than kept.** The SDK’s `kept` reopens history and fails the interrupted turn. `durable` uses persistent history and can continue the turn on reopen from committed checkpoints. The Harness records intent before effects. It never repeats a settled call and will not repeat an ambiguous started call without matching registration and input, repeat-safety promises and confirmed cleanup. Restart is not an automatic wake service. [Recovery](../contracts.md#recovery-and-repeating-work) · [SDK durability](../sdk/placement.md#durability) · [Crash guide](../sdk/guides/05-sessions-that-survive-a-crash.md)
- **Jobs outlive turns, not their session.** A plugin can start a keyed job, take up unfinished work on reopen and report a result as input. Session close cancels jobs; process stop interrupts them. The contract supplies ownership and settlement, not a step scheduler or timer and signal API for durable workflows. [Jobs contract](../contracts.md#jobs) · [Plugin wire jobs](../bindings/plugin.md#jobs) · [SDK jobs](../sdk/api.md#jobs)
- **The plugin set is fixed while a session is open.** `pluginsDuringSession: false` is required, not a setting. Offering registered tools can change without loading a plugin. Setup and replacement are composition operations. `/1` separates processes but grants loaded plugins raw reads of all open sessions in that Harness. It is not an untrusted-code API. [Declaration rules](../contracts.md#declaration-rules) · [Registration](../contracts.md#plugins-and-capabilities) · [SDK plugins](../sdk/api.md#plugins) · [Security](../security.md#plugins) · [Plugin lifecycle](../open-questions.md#plugin-lifecycle)

## Gaps by layer

**(a) Fits inside one agent.** A trusted plugin can run a bounded generated program through one registered tool or a fixed hook handler. Keep scripts as versioned data, give them only checked operations and pin the version for interrupted work. For privileged changes, stage code for review and compose it on the next open. A job owner can wrap one session’s workflow, using a keyed start, its own checkpoint store and explicit cancellation. The engine must not treat the job key as proof that each effect ran only once. A Runtime adapter could use an external engine, but the Harness must remain the authority and effect ledger; do not let the engine retry model or tool effects behind it. None needs a new core capability. [Nested dispatch](../contracts.md#nested-calls) · [Configuration and trust](../contracts.md#configuration-and-trust) · [Jobs](../contracts.md#jobs) · [Runtime records](../bindings/plugin.md#runtime-records-and-effects)

**(b) Needs a spec change if made portable.** Live plugin installation would change [Declaration rules](../contracts.md#declaration-rules) and [Plugins and capabilities](../contracts.md#plugins-and-capabilities): permit a declared change at a defined safe boundary rather than freezing until close. Define versioned activation, approval invalidation, rollback and recovery with old code or explicit refusal. Update the [ACP declaration](../bindings/acp.md#the-declaration), [plugin-set records](../bindings/data.md#session-state) and [plugin handshake](../bindings/plugin.md#starting-the-handshake). [Live state transfer](../open-questions.md#plugin-lifecycle) is a separate gap: name a state schema and migration rule or refuse to hand it over. Untrusted handlers also need a narrower binding and [security rules](../security.md#plugins) with scoped authority and no ambient history reads. A portable workflow that parks independently of a session would need new ownership and wake rules in [Jobs](../contracts.md#jobs), not a reinterpretation of cancellation on close.

**(c) Belongs to a host.** Agent definitions and versions, routing to named instances, waking or moving whole agents across machines, isolation between tenants, and workflows spanning several agents belong above the Harness. A host can use keyed input, follow outcomes and route questions as an authorized actor. A host workflow should not take over the Runtime’s checkpoint or grant itself tool authority. [ADR 0012](../adr/0012-one-agent-is-the-scope.md) · [Host operations](../contracts.md#interface-and-harness) · [Ordered catch-up](../contracts.md#following-a-session)

## Verdict

Start with a fixed sandboxed scripting tool and a session job example that survives a crash without repeating an ambiguous effect. Both are small and exercise existing seams. An external Runtime adapter is medium effort: prove restart, cancellation and lost replies before adding a second engine. Portable parking and live replacement are hard; untrusted hook installation and live state transfer are harder. Wait for a use case that cannot use scripts or review and reopen. Keep the fleet and cross-agent workflow engine in a host.
