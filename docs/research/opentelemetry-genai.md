# OpenTelemetry GenAI and trace context

Primary sources checked **2026-11-22**. The GenAI conventions moved out of the main semantic-conventions repository after v1.41.0. The first standalone [release, v0.1.0](https://github.com/open-telemetry/semantic-conventions-genai/releases/tag/v0.1.0), depends on core conventions v1.45.0. The signals below are **Development**, not Stable. The [standalone changelog](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/CHANGELOG.md) lists breaking changes. The tables below describe `main` at `4181b1ebe55da7edb3538636c45ae64af369b5ef`; the proposed profile pins the release, not `main`.

## Spans

Attribute names below start with `gen_ai.` except `error.type` and `server.*`. All five operations require `operation.name`. `error.type` is conditionally required on failure; it is a class or code, not the error message. These are the main fields; the linked tables give every condition and provider-specific conventions can refine the mapping.

| Span name and kind | Other required fields | Conditional fields and recommendations |
|---|---|---|
| [`invoke_agent {agent.name}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/gen-ai-agent-spans.md#invoke-agent-internal-span), `INTERNAL` | No required Provider field | Agent name and description, conversation ID, data source, output type, choice count and seed when applicable. Recommended: request model and generation parameters, finish reasons and token totals. Intended for the agent entry point, not every internal runner. |
| [`invoke_agent {agent.name}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/client-invoke-agent.md), `CLIENT` | No additional unconditionally required fields | For calling another agent. Agent identity, description and version, conversation ID, data source, Provider, output type, choice count, seed, stream flag and server port are conditional. Recommended: server address, model, request parameters, finish reasons and reported usage. Both kinds can omit the name suffix if unavailable. |
| [`chat {request.model}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/client-inference.md), `CLIENT` (`INTERNAL` allowed for in-process inference) | `provider.name` | Request model and conversation ID when available. Conditional fields also cover output type, named prompt/version, choice count, seed, stream, top-k and port. Recommended: server address, request controls, response ID/model/finish reasons, time to first chunk, usage and cache/reasoning breakdowns. `chat` is the operation for chat APIs; use the actual operation, such as `text_completion`, when different. |
| [`execute_tool {tool.name}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/execute-tool.md#span-gen_aiexecute_tool), `INTERNAL` | `tool.name` | Agent name and conversation ID when applicable. `tool.call.id` is only the ID supplied by the model or Provider. Recommended: tool type and description when known; the description can be sensitive. Arguments and result are opt-in. |
| [`create_agent {agent.name}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/gen-ai-agent-spans.md#create-agent-span), `CLIENT` | `provider.name` | Agent ID if applicable; name, description and version if supplied; model if known; port if address set. Recommended: server address. Instructions are opt-in. For creating an agent through a service, not starting a session. |
| [`plan {agent.name}`](https://github.com/open-telemetry/semantic-conventions-genai/blob/4181b1ebe55da7edb3538636c45ae64af369b5ef/docs/gen-ai/gen-ai-agent-spans.md#plan-span), `INTERNAL` | None beyond operation name | Agent name when available; otherwise `plan`. Emit only for a known planning or decomposition phase. Put the inference that makes the plan under it. Do not infer a planning phase from generic reasoning. |

`gen_ai.conversation.id` correlates messages across operations. Use an existing identifier when the instrumented code manages conversation history or receives the ID from the app. If none exists, omit it. Do not invent an ID, use the trace ID or hash a request. See the [inference notes](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/client-inference.md#spans).

## Content and metrics

The [content rules](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs) treat instructions, messages, completions and tool payloads as sensitive. Capture is off by default. Opt-in selects the signals that receive content. Only signals that define the attribute or allow copying it can carry it. The environment setting, if offered, is `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT` (`NO_CONTENT`, `SPAN_ONLY`, `EVENT_ONLY`, `SPAN_AND_EVENT`). Schema-defined content uses structured `AnyValue`, not a JSON string. The rules allow truncation that preserves structure. External storage and references have a separate opt-in. The streaming-chunk section is still a placeholder.

The historical `gen_ai.client.token.usage` histogram is gone. Its replacements are [token counters and histograms](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/gen-ai-token-metrics.md): `gen_ai.client.inference.usage.input_tokens` and `.output_tokens` are monotonic counters in `{token}`. Record known positive contributions, by `gen_ai.token.modality` (`unknown` if undetermined). Prefer billable counts when both are reported. Cache and reasoning counts are subsets, not extra tokens. The `.operation.input_tokens` and `.operation.output_tokens` histograms describe per-operation distributions, include failures and use zero when usage is unavailable. They are not for computing cost. Metrics are independent of trace sampling.

The seconds histogram [`gen_ai.client.operation.duration`](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/gen-ai-metrics.md#metric-gen_aiclientoperationduration) still exists, but not for inference, embeddings, tool execution or client agent invocations. Use `gen_ai.client.inference.duration`, `gen_ai.client.embeddings.duration`, `gen_ai.execute_tool.duration` and `gen_ai.client.invoke_agent.duration` respectively. Internal agent invocation has `gen_ai.invoke_agent.duration`. Inference duration requires operation and Provider, plus the request model if available and `error.type` on failure.

## What goes on the wire

- **MCP.** [SEP-414](https://modelcontextprotocol.io/seps/414-request-meta) is Final and is in [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic#_meta). It reserves unprefixed `traceparent`, `tracestate` and `baggage` in `params._meta`, with W3C value formats. Their presence is optional. The [OTel MCP conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/mcp.md#context-propagation) prefer message metadata for the MCP parent. HTTP headers cover the HTTP exchange, not individual messages in a stream.
- **ACP.** [v1 extensibility](https://agentclientprotocol.com/protocol/v1/extensibility) recommends reserving those same keys directly in `_meta`. [v2 extensibility](https://agentclientprotocol.com/protocol/v2/extensibility#metadata) reserves them and requires W3C formats when present. Both show `session/prompt` with `params._meta.traceparent`. It is not a key under a vendor namespace. These are upstream ACP versions, not the Modular Agent binding version numbers.
- **A2A.** Its [enterprise guidance](https://a2a-protocol.org/latest/topics/enterprise-ready/) points to W3C headers for HTTP. It does not specify an ACP-style trace field there. The [OTel A2A conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/v0.1.0/docs/gen-ai/a2a.md) describe A2A transport spans, not the agent's internal work.
- **W3C.** [Trace Context](https://www.w3.org/TR/trace-context/) defines `traceparent` as version, trace ID, parent span ID and flags. Reject invalid IDs, including all-zero IDs. Optional `tracestate` carries vendor state. Neither header is for identifiable or sensitive data. A trust boundary can restart the trace. [Baggage](https://www.w3.org/TR/baggage/) is separate application metadata and can disclose sensitive values.

The [OpenTelemetry trace API](https://opentelemetry.io/docs/specs/otel/trace/api/#span-creation) inherits the trace ID from a valid parent. A link alone can point into any trace and does not inherit the ID. Resume needs a saved parent context as well as a link if the resumed span is to stay in the trace and explicitly point back.

The [SDK environment specification](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/) defines `OTEL_SERVICE_NAME`, `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` and `OTEL_SDK_DISABLED`. The [OTLP exporter specification](https://opentelemetry.io/docs/specs/otel/protocol/exporter/) defines the shared `OTEL_EXPORTER_OTLP_*` variables and their per-signal overrides. OTLP/HTTP appends the signal path to the shared endpoint, not to a signal-specific URL.

[OTLP/HTTP JSON](https://opentelemetry.io/docs/specs/otlp/#json-protobuf-encoding) is a wire format, not a required exporter option. The exporter specification makes `http/json` optional. For example, the checked [Go](https://github.com/open-telemetry/opentelemetry-go/blob/v1.47.0/exporters/otlp/otlptrace/otlptracehttp/client.go) and [Python](https://github.com/open-telemetry/opentelemetry-python/blob/v1.45.2/exporter/opentelemetry-exporter-otlp-proto-http/src/opentelemetry/exporter/otlp/proto/http/trace_exporter/__init__.py) OTLP/HTTP exporters encode spans as binary Protobuf. The shared check can use a JSON exporter confined to test fixtures without requiring JSON export in `ma`.
