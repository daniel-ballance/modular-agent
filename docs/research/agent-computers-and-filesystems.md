# Computers and filesystems for agents

Checked 2026-11-22. This note uses first-party pages, release notes and repositories read directly. Search and documentation-index snippets were used only to find sources. No services were tried. I could not verify John Suh's X post directly; the proposal below is the one in the task brief. “Available” means there is a documented way to use it, not that the vendor declared general availability (GA).

## What is available

**Claude Code: Remote Control and cloud sessions.** [Remote Control](https://code.claude.com/docs/en/remote-control.md) lets a browser or phone drive a running Claude Code process on your machine. The files and commands stay there. One Remote Control server can run sessions in the same directory or in separate Git worktrees. [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web.md) instead runs a session in an isolated managed VM by default. `--cloud` starts a cloud session with a repository checkout or bundle; `--teleport` brings back conversation state and can fetch the branch, not the VM's memory. Both features are available on listed plans. [Routing cloud sessions to your own runners](https://code.claude.com/docs/en/self-hosted-environments.md) is a separate public beta for Team and Enterprise.

**Cursor Background Agents, now Cloud Agents.** Background Agent [went GA in June 2025](https://cursor.com/changelog/1-0). [Cloud Agents](https://cursor.com/docs/cloud-agent.md) run in isolated VMs, work on separate branches, and can use the desktop and browser. An environment can start from a saved setup snapshot or a Dockerfile and can contain several repos. I did not find a public API to clone a live agent's memory. [Self-Hosted Machines](https://cursor.com/docs/cloud-agent/self-hosted.md) run file, shell and computer-use tools on your worker while Cursor still runs the agent loop.

**Cua AI.** [Cua Spaces](https://cua.ai/docs/spaces/concepts/machines-and-spaces.md) is a released [desktop app](https://github.com/trycua/cua/releases/tag/cua-spaces-v0.41.3). A computer can share its real desktop or host several isolated Spaces. The [SDK](https://cua.ai/docs/cua-sdk/guides/local-runtimes.md) also targets machines you own in the cloud and providers such as E2B, Daytona and Modal. The [local checkpoint API](https://cua.ai/docs/cua-sdk/reference/sandbox/checkpoints.md) saves disk and memory for microVMs and filesystem state for containers; forks make new sandboxes. [Batch forks](https://cua.ai/docs/cua-sdk/reference/sandbox/fork-batch.md) can place them across machines. [Driver permissions](https://cua.ai/docs/cua-driver/guides/permissions.md) gate computer-use calls, not all code running as the same desktop user.

**E2B.** A programmable cloud sandbox. Its available [snapshot API](https://docs.e2b.dev/sandbox/snapshots.md) captures disk and memory and starts new sandboxes from the saved state. [Fork](https://docs.e2b.dev/sandbox/fork.md) does both in one call and drops active connections during capture. Pause/resume is for the same sandbox, not an independent copy. [Disk-only snapshots](https://docs.e2b.dev/sandbox/filesystem-only-snapshots.md) cold-boot and need project enablement.

**Daytona.** A programmable [container and VM sandbox service](https://www.daytona.io/docs/en/sandboxes.md). The available [snapshot API](https://www.daytona.io/docs/en/snapshots.md#create-snapshot-from-sandbox) creates reusable cold snapshots for containers and cold or hot snapshots for Linux and Windows VMs. Hot snapshots capture memory as well as files. The [fork operation](https://www.daytona.io/docs/en/sandboxes.md#fork-sandboxes) duplicates VM state into an independent sandbox. Containers must use snapshot-and-create instead.

**Modal Sandboxes.** Programmable environments for running code. The available [snapshot APIs](https://modal.com/docs/guide/sandbox-snapshots) can start new sandboxes from a root filesystem image or mount a saved directory. Root snapshots exclude mounted volumes. The memory clone API is experimental. It captures filesystem and memory but does not support snapshotting with an outstanding exec or reliably restore its background processes.

**Morph Cloud.** A hosted VM service with a [published SDK](https://pypi.org/project/morphcloud/) and [deployed API](https://cloud.morph.so/docs/documentation/overview). [Snapshots](https://cloud.morph.so/docs/documentation/instances/creating-snapshot) capture memory and disk, including running processes. [Branch](https://cloud.morph.so/docs/api-reference/branch-instance-instance-instance-id-branch-post) takes one internal snapshot and starts multiple child instances from it. I did not find a GA statement for these operations.

**Fly Machines.** Available VMs with [Machine clone](https://docs.fly.io/flyctl/cmd/fly_machine_clone). Clone copies the Machine configuration; an attached volume is empty by default or can be populated from a volume snapshot. [Volumes](https://docs.fly.io/volumes/overview.md) are host-local and support independent forks. [Suspend](https://docs.fly.io/machines/api/machines-resource#suspend-a-machine) snapshots memory for a best-effort resume of the same Machine. I did not find a way to clone that memory snapshot into another Machine.

**Cloudflare Sandbox.** [Available on Workers Paid](https://developers.cloudflare.com/sandbox/index.md), with Linux containers and a separate Dynamic Workers option. Linux sandbox scheduling via Durable Objects and [container snapshots](https://developers.cloudflare.com/sandbox/files/save-and-restore-a-workspace/index.md) are in public beta. A container snapshot saves the writable root, not mounts, RAM or processes. A new sandbox of the same Durable Object class can start from that snapshot ID. [Directory backups to R2](https://developers.cloudflare.com/sandbox/reference/directory-backups/index.md) are narrower file copies.

**Archil.** A shared POSIX disk service independent of compute, with an [existing bucket option](https://docs.archil.com/guides/storage/mount-existing-bucket.md). [Disk checkpoints and writable branches](https://docs.archil.com/concepts/branches-and-checkpoints.md) are GA in its AWS regions and require its flat-block format. A disk mount is authorized by IAM or a disk token; [it grants the mounting server the whole disk](https://docs.archil.com/concepts/authorization.md), even though POSIX permissions apply. Its separate Firecracker sandbox service is [GA](https://docs.archil.com/reference/changelog.md). [Forks](https://docs.archil.com/api-reference/sandboxes/fork-sandbox.md) from running or paused VMs copy CPU, memory and root disk state; stopped sources cold-boot. Sandboxes with extra mounts must be stopped before forking, and the fork mounts the same extra disks.

**Amazon S3 Files.** [GA since April 2026](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-s3-files/). It mounts a versioned S3 bucket on AWS compute via NFS with POSIX semantics, file locking and [access points that can enforce POSIX identities](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files.html). [Synchronization](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html) is asynchronous; S3 wins conflicts between the bucket and the filesystem. Object versions are not a directory checkpoint or a VM clone.

**JuiceFS.** A released [open-source filesystem](https://github.com/juicedata/juicefs). It stores file contents as blocks in object storage such as S3 and keeps names, locks and other [filesystem metadata](https://juicefs.com/docs/community/architecture/) in a separate engine. Unlike S3 Files, the backing objects are not the original directory tree. [POSIX ACLs](https://github.com/juicedata/juicefs/blob/main/docs/en/security/posix_acl.md) can be enabled per volume since 1.2. It is storage, not a VM checkpoint service.

## Patterns and disagreements

- **Placement is not migration.** Claude Remote Control moves the UI; Cursor workers move tool execution; Cua exposes explicit machine targets. One agent can use several machines by calling tools on each. Many agents can use one physical host with separate sandboxes or worktrees. Sharing a live checkout or desktop is different: writes and input can collide. [Claude spawn modes](https://code.claude.com/docs/en/remote-control.md#start-a-remote-control-session), [Cursor workers](https://cursor.com/docs/cloud-agent/self-hosted.md), [Cua Spaces](https://cua.ai/docs/spaces/concepts/machines-and-spaces.md).
- **Name the state being copied.** An image seeds a clean start. A disk or directory snapshot saves files. A live VM checkpoint can copy processes. None makes an external side effect reversible. Shared mounts can remain shared after a fork. [Modal snapshots](https://modal.com/docs/guide/sandbox-snapshots), [Archil fork](https://docs.archil.com/api-reference/sandboxes/fork-sandbox.md).
- **Version control is not an access boundary.** For per-directory history, use a repository per versioned tree. [Git worktrees](https://git-scm.com/docs/git-worktree) and [jj workspaces](https://docs.jj-vcs.dev/latest/working-copy/#workspaces) give separate checkouts of one repo, with shared repository state. Neither turns a shared mount into an ACL. An access point, disk grant or POSIX ACL controls storage access independently of VM placement. [S3 Files](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files.html), [Archil authorization](https://docs.archil.com/concepts/authorization.md), [JuiceFS ACLs](https://github.com/juicedata/juicefs/blob/main/docs/en/security/posix_acl.md).
- **Agent identity versus turn initiator is a policy choice.** A fixed service identity is simple but every authorized turn inherits its storage reach. Delegated access should intersect the agent's ceiling with the initiating actor's permissions, then narrow further for steering, releases and continuations. Never let a model-supplied identity decide. The storage docs describe mount principals or POSIX users, not this turn mapping. [S3 Files](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files.html), [Archil authorization](https://docs.archil.com/concepts/authorization.md), [MA authority](../contracts.md#authority).

## What Modular Agent has today

- **One selected working environment per session.** The project is the working folder, not the machine. The SDK defaults to a local environment and exposes file I/O, shell execution, cleanup and optional listing and points. `commandContainment` says which processes stop; `confinesFiles` says whether file operations stay in the project after resolving symlinks. The local SDK environment does not claim file confinement. Neither field confines what a shell command can reach. [Architecture](../architecture.md#working-environment), [selection](../contracts.md#plugins-and-capabilities), [containment](../contracts.md#the-working-environment), [SDK declarations](../sdk/api.md#the-declaration) and [environment methods](../sdk/api.md#the-other-parts).
- **Served environments.** The SDK can serve an environment over authenticated WebSocket, with TLS off loopback and connection-local plugin instances. `/1` binds a connection to one canonical project in the environment's path syntax. Loss requires cleanup in scope; the connection does not resume. The repo reports loopback tests, not deployment across machines. [SDK services](../sdk/placement.md#services), [transport](../bindings/websocket.md), [paths](../bindings/plugin.md#paths-and-points), [README](../../README.md#known-gaps).
- **Rewind is project-file restore.** `ma` saves tracked and non-ignored untracked files in Git with a private index and refs. It does not change the user's index or branches. The Harness checks points before an in-place rewind and refuses if another hosted session uses the project. Operators must not enable rewind for a project shared by agents in different processes. A session fork does not copy live work. [Git points](../reference/standard-configuration.md#rewind-points), [rewind rules](../contracts.md#moving-and-rewinding), [operator rules](../security.md#what-an-operator-configures).
- **Actor rights gate actions, not filesystem syscalls.** The Harness authenticates project and tenant scope, records who caused and authorized work, and checks starting rights against current rights and ceilings. An actor of kind `agent` is a session principal, not automatically a filesystem user. `/1` environment requests carry session and paths, not effective per-effect actor authority. [Actors and authority](../architecture.md#actors-and-authority), [SDK actors](../sdk/api.md#actors-and-rights), [environment wire](../bindings/plugin.md#the-host-asks-the-working-environment), [connection scope](../security.md#connection-scope).

## Gaps and verdict

### A. Fits inside one agent

- **Low to medium:** Prove one served sandbox on two machines, including disconnect cleanup. Mount a separate disk under the same canonical project path. Use a fixed, least-privilege storage identity per agent or session, and separate writable checkouts for concurrent work. Use separate grants or mounts if checkouts need different access rights. Add Git or jj workspace setup as a plugin. A backend can implement file-only points if it meets the existing probe and in-place restore rules. [SDK placement](../sdk/placement.md#services), [paths and points](../bindings/plugin.md#paths-and-points).
- **Medium:** Add explicitly targeted desktop or shell tools, or a private capability with a composite environment behind the existing single slot. Keep ordinary project I/O on a stable root. Make target identifiers, cleanup and retry policy explicit. No need to expose a second default environment. [Plugin capabilities](../contracts.md#plugins-and-capabilities), [SDK contexts](../sdk/api.md#contexts), [recovery](../contracts.md#recovery-and-repeating-work).

### B. Needs a spec or binding change to be portable

- **Medium to high: first-class targets.** In [Plugins and capabilities](../contracts.md#plugins-and-capabilities) and [Harness and working environment](../contracts.md#harness-and-working-environment), add explicit target selection and pin target identity to effects and recovery. A binding-only profile could keep one logical environment and map a logical project to approved backend roots. It would have to replace `/1`'s [single canonical path rule](../bindings/plugin.md#paths-and-points), not bypass it.
- **High: delegated filesystem rights.** Extend [Authority](../contracts.md#authority) and [environment requests](../bindings/plugin.md#the-host-asks-the-working-environment) with a verified effect scope derived by the Harness. Specify expiry, revocation, mixed-actor work and long-lived processes. Enforce the same scope for shell and file calls. Pin the ceiling at admission and recheck it before effects. Use restricted mounts or kernel identities so a shell cannot bypass the same policy. Keep the authenticated storage identity and the actor provenance distinct in the audit record.
- **High: portable live checkpoints.** Keep them separate from [rewind](../contracts.md#moving-and-rewinding). Add a checkpoint/fork contract that declares what is captured and how mounts, lineage and fencing work. Update [recovery](../contracts.md#recovery-and-repeating-work) if restored processes can keep doing work: a clone is not proof the original stopped or that a call is safe to repeat.

### C. Belongs above one agent

**High:** A host can place whole agents on a fleet, allocate and clone their sandboxes, enroll people's computers, and assign storage grants. It also owns coordination among independent writers. Do not enable shared-project rewind under the current rules. A future exception would need to change both [Moving and rewinding](../contracts.md#moving-and-rewinding) and the [operator rule](../security.md#what-an-operator-configures), with fencing that covers every writer. [ADR 0012](../adr/0012-one-agent-is-the-scope.md) keeps that orchestration outside the Harness.

**Verdict:** Start with a served sandbox and an independently mounted project. Give concurrent agents separate writable checkouts before sharing a live tree. These buy remote placement and durable files without a new core rule. Defer portable multi-target routing until there is a second implementation to compare. Leave live cloning and delegated filesystem rights until a deployment needs them and can enforce them.
