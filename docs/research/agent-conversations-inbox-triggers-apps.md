# Agent conversations, inboxes, triggers and apps

Checked 2026-11-22. The product facts below come from public first-party pages, posts, specs or repositories I read. Search snippets were leads, not evidence. I did not sign in or test products. The brief supplies John Suh’s “Agent platform 2027” thesis; I did not verify the original post. Product behavior is not proof of how the runtime implements it.

## What exists

**Duet.** Claude Duet is a waitlisted research preview for eligible US subscribers, on web and in its own mobile app. A single ongoing text or voice thread accepts work and receives briefings, results and approval requests. Duet checks connected apps in the background and asks before actions such as sending or deleting. Anthropic describes the thread, not a separate session record or a posting tool. [Announcement](https://claude.com/resources/articles/claude-duet) · [Current product page](https://claude.com/product/claude-duet)

**Grok Bot.** This is xAI’s cloud-computer agent product, not the Grok model chat. It shipped in beta for eligible subscribers. Users message Bots, which can delegate to one another, run scheduled routines and ask for approval. The documented chat transcript includes tool activity, questions and approval cards alongside messages; it is not just a feed of explicit posts. I found no general-availability claim. [Launch](https://x.ai/news/introducing-grok-bot) · [Chat](https://docs.x.ai/grok-bot/chat-and-collaboration) · [Routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)

**Dots.** OpenAI’s primary dot is a persistent personal assistant with its own computer. One conversation can delegate several tasks; Activity shows background work, and cloud Codex threads can also be opened separately. Auto-review decides which actions need approval or handoff. The current guide says gradual rollout to eligible Pro and Business Premium accounts and general availability in eligible Enterprise, Edu and Healthcare workspaces. Specialist dots with separate identities were announced as a preview, not the same rollout. [Launch](https://openai.com/index/introducing-dots/) · [Current guide](https://learn.chatgpt.com/docs/dots)

**Microsoft Today.** Nicolas Bustamante (@nicbstme) identified Today at Ignite as a Microsoft feed for Outlook and Copilot, not a chat box. An agent works in the background on email, calendar, Teams and documents. The feed presents drafts, conflicts and items to review or act on. I read his full [announcement post](https://x.com/nicbstme/status/2123481166737289514). I did not find a public availability or preview statement I could verify, so this is an announced product in this note.

**Claude Code Monitor.** The shipped client tool watches a background command’s output lines or incoming WebSocket messages and feeds them into the active session. Claude can write the watch script on demand. Watches are time-bounded and end with the session; plugins can also declare monitors. This is not a persistent tenant event service. [Monitor docs](https://code.claude.com/docs/en/tools#monitor-tool)

**Claude Code Channels and scheduled tasks.** Channels push events from configured plugins into an already-running session. In Anthropic’s example, Claude calls a channel’s `reply` tool; the reply text appears in the external chat while the terminal shows the call and confirmation. Scheduled tasks run in the cloud on a schedule, an API call or a GitHub event without keeping that session open. Both are documented research previews. [Channels](https://code.claude.com/docs/en/channels) · [Scheduled tasks](https://code.claude.com/docs/en/routines)

**Zapier Zaps.** A shipped Classic Zap is a trigger followed by one or more actions; a Run Agent action can pass results into later steps. Next Gen Zaps are in early access by request. An AI client can define and deploy a workflow that Zapier runs after that chat closes. Agentic and deterministic steps can share one workflow. [Classic integration](https://help.zapier.com/hc/en-us/articles/35859160812685-Start-an-agent-from-a-Zap) · [Next Gen](https://help.zapier.com/hc/en-us/articles/48391476448141-Get-started-with-Next-Gen-Zaps) · [Migration guide](https://help.zapier.com/hc/en-us/articles/47402591569805-Migrating-from-Agents-to-AI-by-Zapier)

**Zapier Agents.** The existing Agents product documents published agents started on demand, by schedule, by app event, or by Zap or MCP call. Publishing activates a configured trigger; the Activity tab records runs. An agent can notify a user to come back and approve, or the Zap can use a separate Human in the Loop step. [Triggers](https://help.zapier.com/hc/en-us/articles/45394909914381-Set-up-your-agent-s-trigger) · [Approvals](https://help.zapier.com/hc/en-us/articles/41776074420493-Add-approval-steps-to-your-agent-s-instructions)

**Rex.** Superlogical’s Rex is a terminal multiplexer in public beta testing. Its Program Status Protocol lets a program report completion or that it is blocked on permission, a question or authentication. Lua scripts can react to Rex events and custom actions can ask questions in the command palette. These are terminal status and scripting surfaces, not evidence of a common approval queue. [Beta](https://www.superlogical.com/updates/public-testing-beginning) · [Program status](https://www.superlogical.com/rex/docs/build/program-status) · [Lua events](https://www.superlogical.com/rex/docs/automate/lua-events) · [Custom UI](https://www.superlogical.com/rex/docs/customize/custom-ui)

**OpenCode’s Rune.** Anomaly, the OpenCode maker, publishes Rune as a Rust UI framework. It includes OpenCode UI examples and lets agents render, inspect and drive apps headlessly. It is usable from source; I found no tagged release or first-party per-user app store. The separate [Rune Browser](https://github.com/nayupls1/rune-browser) does build personal mini-apps and supports the OpenCode CLI, but is not Anomaly’s Rune. [Anomaly repository](https://github.com/anomalyco/rune) · [Releases](https://github.com/anomalyco/rune/releases)

**Claude Artifacts.** This shipped feature opens editable documents, designs or small apps beside the conversation and saves them in an Artifacts tab. Published chat artifacts can be copied by eligible users. Users of connected apps normally use their own connections. Export and copying do not imply a shared POSIX tree or an automatic source fork for every viewer. [Artifacts help](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them) · [Sharing](https://support.claude.com/en/articles/9547008-share-artifacts)

**ChatGPT Apps (Apps SDK).** Apps shipped in chat; OpenAI opened directory submissions and described the SDK as beta. Apps use developer-provided MCP tools and can show interactive UI. The [Apps SDK landing page](https://developers.openai.com/apps-sdk/) now redirects to docs for ChatGPT and Codex plugins, which describe MCP servers and optional UI. I found no general per-user source-fork promise. [Launch](https://openai.com/index/introducing-apps-in-chatgpt/) · [Directory](https://openai.com/index/developers-can-now-submit-apps-to-chatgpt/) · [Current docs](https://developers.openai.com/plugins)

**MCP Apps.** This is a released MCP extension, not an app builder. A tool links to a `ui://` resource in its metadata. A supporting client fetches it, renders it in a sandboxed iframe and mediates calls from that view. Rendering and permission to call a tool are separate. [Release](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/) · [Spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

**AG-UI.** A published agent-to-application event protocol with released libraries. It carries runs, messages, tool calls and state. A frontend tool can be left unanswered at run end; the app executes or declines it, then supplies the matching result for a later run. That differs from a server tool asking a question. [Overview](https://docs.ag-ui.com/introduction) · [Tool calls](https://docs.ag-ui.com/spec/1.0/events/tool-calls#frontend-tools) · [Releases](https://github.com/ag-ui-protocol/ag-ui/releases)

**A2UI.** A published generative UI protocol (v1.0 in the current docs). The agent sends component and data updates. The client renders from its catalog and sends actions back. It is not a session protocol; it can also carry an MCP App in an explicit embedded surface. [Spec](https://a2ui.org/specification/v1.0-a2ui/) · [Embedding guide](https://a2ui.org/guides/mcp-apps-in-a2ui/)

## Patterns and disagreements

- **A conversation is a product record, not necessarily a trace.** [Duet](https://claude.com/product/claude-duet) uses one thread, [Dots](https://learn.chatgpt.com/docs/dots) gives delegated work separate surfaces, [Grok Bot](https://docs.x.ai/grok-bot/chat-and-collaboration) shows work in the transcript, and [Today](https://x.com/nicbstme/status/2123481166737289514) starts with a feed. [Claude Code Channels](https://code.claude.com/docs/en/channels) shows explicit tool-call posting on one route, not a product-wide rule that every user-visible message must be a post.
- **Attention and authorization differ.** [Rex](https://www.superlogical.com/rex/docs/build/program-status) signals blocked work; [Grok Bot](https://docs.x.ai/grok-bot/approvals-security-and-privacy) offers approval cards tied to actions. A merged inbox can collect both approvals and questions, but its feed entry is not itself an authorization grant.
- **Watch, trigger and workflow have different lifetimes.** [Monitor](https://code.claude.com/docs/en/tools#monitor-tool) feeds a live session. [Next Gen Zaps](https://help.zapier.com/hc/en-us/articles/48391476448141-Get-started-with-Next-Gen-Zaps) deploy a trigger and workflow independently of the chat. Neither establishes an agent-defined, tenant-wide WSS, Kafka and CDC contract.
- **An app view is not an app fork.** [Artifacts](https://support.claude.com/en/articles/9547008-share-artifacts) support copying within the product. [MCP Apps](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) serve MCP server-supplied UI code; [A2UI](https://a2ui.org/specification/v1.0-a2ui/) primarily describes host-rendered components. Neither protocol specifies a per-user source tree.

## What Modular Agent has today

- **Interface and views.** An authenticated [Interface](../contracts.md#interface-and-harness) submits keyed input, follows a session and lists or answers questions. The [SDK](../sdk/api.md#sessions-and-turns) exposes these session operations; it also supports custom [Interface plugins](../sdk/api.md#the-other-parts). [Following](../contracts.md#following-a-session) replays kept entries then follows live events. The Harness authorizes each recipient view before the [output gate](../contracts.md#the-output-gate) can withhold or redact it, including on replay. It does not make a second conversation record or prove delivery. [ACP updates](../bindings/acp.md#sessions) lack the core follow cursor; an ACP host must reconcile against kept history rather than assume a lossless notification stream.
- **Inbox primitives.** [SDK questions](../sdk/api.md#questions) can be listed and answered later. With declared support a non-approval question may outlast its turn and enable a continuation. Approvals cannot outlast the turn and require a present, eligible answerer with the exact, unchanged call view on the answering route. See [Questions](../contracts.md#questions), [Approval policy](../contracts.md#approval-policy) and the [ACP guide](../sdk/guides/08-drive-an-agent-over-acp.md).
- **Watchers and event input.** [Jobs](../contracts.md#jobs) belong to a session, can outlive a turn, and are cancelled on close. A job report becomes ready input only with declared support; otherwise it is parked for authorized release. The [SDK](../sdk/api.md#jobs) offers start, progress, end and optional resume. A schedule or webhook instead [gives input as an actor](../architecture.md#jobs). [Tenants](../contracts.md#limits-and-tenants) set scope, rights ceilings and optional soft token budgets; the [SDK option](../sdk/api.md#building-an-agent) does not provision listeners.
- **Pass-through and calls.** [Content](../contracts.md#content) can carry typed MCP Apps or A2UI data; [shared data](../bindings/data.md#content) keeps unknown types inert, subject to projections and gates. [Presentation hints](../contracts.md#tool-definition) are not resource access. The [SDK direct call](../sdk/api.md#sessions-and-turns) uses the Harness and its gates, but [out-of-turn results](../open-questions.md#tool-calls-outside-a-turn) do not enter portable model context by default. [Tools run by an Interface](../open-questions.md#tools-run-by-an-interface) have no portable profile.

## What is missing

**(a) Fits within one agent.** Add a registered `post_to_conversation` tool that returns a typed post. An Interface projects only committed, gated posts into its conversation and keys them by source entry ID to deduplicate replay. Keep audience and source identities with the post. Do not send raw tool output directly to the user. Keep the session as a separate, authorized debug view. Prototype an inbox using the existing question and answer operations. A preloaded watch plugin can accept bounded source and filter settings at run time, then run a session job or submit keyed input as a configured actor. Do not load generated plugin code into an open session: the [plugin set is fixed](../contracts.md#plugins-and-capabilities). Start file-backed apps as ordinary project files with explicit copy and render actions. An A2UI renderer or AG-UI adapter can be an Interface; broader wire support is a binding choice, not a reason to change the turn loop.

**(b) Needs a spec change for portable behavior.** For an interoperable MCP Apps bridge, extend [Interface and Harness](../contracts.md#interface-and-harness) and [Harness and tool source](../contracts.md#harness-and-tool-source) with scoped, gated resource retrieval. Extend [Tool dispatch](../contracts.md#tool-dispatch) and a binding to identify and limit app-originated calls, check visibility, and enforce rights without giving the app the viewer’s full authority. For AG-UI-style client execution, define a distinct Interface executor with exact call and result binding, deadlines and recovery. To import its result, change [Context and interrupted work](../bindings/data.md#context-and-interrupted-work) to admit only results matched to recorded calls, not arbitrary client history. Ordinary UI-triggered server calls do not need that context change. To let approvals survive the turn, change [Questions](../contracts.md#questions) and [Approval policy](../contracts.md#approval-policy) to define durable pending approval and recheck the exact call, registration, current rights, route and expiry at dispatch. Do not convert a late answer to a text question into approval.

**(c) Belongs to a host.** Under [ADR 0012](../adr/0012-one-agent-is-the-scope.md), a conversation or inbox spanning whole agents belongs above their Interfaces. Keep source identity, recheck answerability, and route answers to the source agent; do not turn a copied card into authority. The host also owns persistent tenant subscriptions independent of sessions, including identity, quotas, cursor or offset recovery, deduplication and revocation. A stable upstream event ID can key agent input; it does not make offset commits and agent admission one transaction. Run agent-authored filters under operator policy; treat event payloads as data. For shared apps, let a user or an authorized agent fork a named revision into an owned tree and edit it without changing the original. Serving those forks across tenants needs file ownership, versioning, revocation and execution isolation. The [working environment](../contracts.md#the-working-environment) is a seam for files, not that service.

## Verdict

Start with gated posts, a live inbox over existing questions, and one keyed event adapter. These are low-cost and test the separation from session history without changing the core. A bounded watch job, file-copy preview and multi-agent conversation or inbox are medium work; the host must handle reconnects and stale approvals without losing source identity. Portable app actions and client-executed results are harder because they cross trust and recovery boundaries. Durable approvals, tenant-wide streams and hosted app forks are the highest-cost gaps. Defer them until the simpler prototypes show a need.
