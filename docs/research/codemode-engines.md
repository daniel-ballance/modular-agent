# Codemode engines, checked 2026-11-21

Which engine should the Rust, TypeScript, Go and Python builds of `ma` use? **Keep Monty Python and use the pinned Monty native worker.** Go can drive that worker without cgo or a second interpreter. Use JavaScript on one purpose-built QuickJS-NG WASM module as the fallback if we decide to change the language or need one binary artifact across platforms as well as across languages. Do not select four convenient bindings and assume that they agree.

## What was judged

[One reference product](../adr/0026-one-reference-product.md) means the same accepted scripts, tool calls, structured values or fallback text, failures, and model-visible output. The [Tools contract](../reference/standard-configuration.md#tools) specifies one model tool, nested dispatch through the agent, positional or keyword arguments in schema order with `None` meaning omitted, ordinary tool failures raised in the script (`exec` non-zero is data), `describe_tool` and `search_tools`, printed output plus the last expression, and fresh state. It specifies 30 seconds of computation **between** nested calls, 256 MiB of interpreter allocations, 500 nested calls excluding discovery, recursion depth 200, 1 MiB printed output, and truncation at 2,000 lines or 50 KB (the Rust implementation uses 50 × 1024 bytes). No ambient file, network, clock or process access. Memory and time failures are terminal; cancellation ends the run, and a dead interpreter must not bring down the agent. The worker must be an OS process: WASM memory or a JavaScript worker thread alone is not enough. The existing [reference checks](../../conformance/reference/run.mjs) test file read/write via hidden nested calls and memory failure followed by a working next run, not all of this contract.

For every candidate, the adapter still owns schema validation, argument mapping, the 500-call counter, print metering before buffering, result truncation and cancellation of nested work. Put these checks on the worker/agent boundary, bound IPC frames and decoded values on both sides, and do not rely on an exception a script can catch to enforce a terminal limit. Separate a compute watchdog (off while genuinely waiting on a tool) from session cancellation (always on); discovery must not provide unlimited compute resets. Do not retry tool calls after worker death. Process isolation contains faults; a minimal environment, no inherited handles except control pipes, and OS restrictions where available are separate from keeping APIs out of the language.

Package dates below are stable releases or, where there is no tagged release, the registry's selected revision. Maintenance assessments are based on the release/source history, not guarantees of future support. Model fluency is a judgment about short scripts, not a measured ranking: no model calls were made. Python and JavaScript look easiest to prompt, with Python already in use in `ma` and JavaScript in Pi. Lua likely needs more examples, especially for tables and indexing; Starlark looks like Python but requires examples showing what Python syntax is *not* allowed.

## Monty: the same Python, with a different Go client

**What ships.** The active MIT project released [1.6.0 on November 11](https://github.com/pydantic/monty/releases/tag/v1.6.0); these are the pins in [`ma` Rust](../../rust/crates/tools-code/Cargo.toml), [TypeScript](../../typescript/packages/ma/package.json) and [Python](../../python/packages/ma/pyproject.toml). Rust builds the native worker with [`monty-runtime`](https://crates.io/api/v1/crates/monty-runtime/1.6.0) and uses [`monty-pool`](https://crates.io/api/v1/crates/monty-pool/1.6.0); Node's [`@pydantic/monty`](https://registry.npmjs.org/@pydantic/monty) supplies platform packages and a `./wasm` export; Python's [`pydantic-monty`](https://pypi.org/project/pydantic-monty/1.6.0/) brings the native [`pydantic-monty-client`](https://pypi.org/project/pydantic-monty-client/1.6.0/) and worker distribution. The standalone executable is **`monty subprocess`**, not a new Go binding or a Python CLI shim. The [CLI docs](https://github.com/pydantic/monty/blob/v1.6.0/docs/cli.md#subprocess-mode) describe the mode; the [binary target](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-runtime/Cargo.toml) builds it and [`pydantic-monty-runtime` wheels](https://pypi.org/project/pydantic-monty-runtime/1.6.0/#files) ship it. The GitHub release itself has no attached binary. `ma` can ship the worker as a sibling executable per target, independently of Python or Node; Go needs a native worker artifact but not a C or Rust toolchain at install time if we ship one.

**Go through framed stdio.** [`monty-proto` 1.6.0](https://crates.io/api/v1/crates/monty-proto/1.6.0) has a [protocol guide](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-proto/README.md), a [`.proto`](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-proto/proto/monty/v1/monty.proto), and [framing code](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-proto/src/frame.rs) (four-byte little-endian length, then protobuf). 1.6.0 [speaks version 8 and accepts 7–8](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-proto/src/lib.rs); it declares a version on `Configure`, rejects mismatches with the supported range and exits, with no negotiation handshake. This is a documented, versioned interface, not a promise of indefinite or semantically identical interoperation. Pin worker, schema and tested profile together. Skip gRPC, dumps, relay features and async streaming for `ma` unless needed later.

A production Go client needs generated message types, a bounded frame reader, validation of the flat post-order value arena (including types, child indices, expanded size and host conversions), `Configure`/`Feed`/print/complete/error handling, and a context-aware supervisor that kills/reaps the child. Publish one `tools` host module both as a global and in the import handler; its attributes are actual host function values. A normal Python call emits `FunctionCall` with positional and keyword roots into the arena; the worker stops, Go awaits the nested call, and `ResumeCall` delivers the value or raised `RuntimeError`. Handle `NameLookup` and the small allowlist of `OsCall`s; do not answer arbitrary names/imports with capabilities. Keep script-level calls synchronous, including aliases; the [host function](https://github.com/pydantic/monty/blob/v1.6.0/docs/host-functions.md) and [host object](https://github.com/pydantic/monty/blob/v1.6.0/docs/host-objects.md) docs also distinguish optional Python async behavior. Use a common value/error profile (large ints, bytes, non-finite floats, cycles, invalid names, diagnostic rendering), not the host language's default JSON conversions. The protocol guide documents the Rust decoder's separate frame and allocation budgets; a generated Go decoder by itself does not reproduce those protections.

**Limits and cost.** [`ResourceLimits`](https://github.com/pydantic/monty/blob/v1.6.0/docs/resource-limits.md) provides a per-turn clock (resets on feed/resume), per-feed clock (cumulative, not the same as the product's per-nested-call limit), interpreter memory and Python depth. Memory/time invalidate the run; `RecursionError` is catchable. Native workers also have an allocator backstop (with headroom; not an RSS limit), and [`monty-pool`](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-pool/README.md) adds a hard watchdog and discards unsafe sessions. Its optional externally supervised CPU clock for local subprocesses is Linux-only; wall-mode active-turn deadlines are portable but include scheduling, and are not literal CPU accounting. Set a common clock policy, never count host waits, and explicitly specify what happens with non-tool suspensions. Do not use upstream `max_suspensions` as the 500-tool limit: it also sees discovery, imports and name lookups. Configure `OsPolicy` and refuse OS calls except the `tools` import: Monty [allows clock, entropy and sleep by default](https://github.com/pydantic/monty/blob/v1.6.0/docs/security.md#the-clock). Delegate wall clocks and sleep to a host that denies them, keep process and thread clocks zero (`OsPolicy.process_time`), and delegate entropy or seed it. A fixed wall time is also possible if the product explicitly wants one. The host caps streamed prints and rendering; bare worker exit needs stable mapping to memory, timeout, cancellation, or unexpected death. Native transport costs serialization and a pipe round trip per call. A pool can prewarm workers, but begin with one session per process, and measure before pooling. The Go spawn measurement is below.

**WASM instead.** Monty's [build script](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-js/scripts/build-component.mjs) compiles a `wasm32-wasip1` reactor, adapts it into a WASI 0.2 component and uses Jco to produce JS glue and several core modules; the [WIT](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-wasm-runtime/wit/runtime.wit) exports the worker state machine, not stdio or just a `run(code)` import. It uses [the same Monty worker logic and allocator controls](https://github.com/pydantic/monty/blob/v1.6.0/crates/monty-wasm-runtime/src/lib.rs) but wall-mode only, WIT lifting/lowering and copies, and still needs supervision, fresh instances and explicit guest OS policy. [wazero](https://pkg.go.dev/github.com/tetratelabs/wazero) supports core Wasm and Preview 1; its documented API is not a drop-in host for the component or its JS glue. For Go, either port the canonical ABI and imports for the core reactor (or Jco's plumbing for all its modules), or build a small core-WASM shim exposing bounded byte buffers and the protobuf worker state machine. For all four, using that shim would mean Go+wazero, Rust/Python+Wasmtime, Node+core `WebAssembly`, still inside subprocesses. It could share one engine artifact, but adds linear-memory and adapter validation, compilation/instantiation and another time/interrupt layer; no startup measurement. No Go/component end-to-end path was verified.

**Upgrade `gomonty` instead.** [`gomonty` v0.0.14](https://pkg.go.dev/github.com/ewhauser/gomonty@v0.0.14) (March 29, MIT) loads bundled native libraries through `purego` without cgo; [release assets](https://github.com/ewhauser/gomonty/releases/tag/v0.0.14) are platform-specific. The [tag pin](https://github.com/ewhauser/gomonty/blob/v0.0.14/Cargo.toml) is Monty 0.0.9; the [latest module record](https://proxy.golang.org/github.com/ewhauser/gomonty/@latest) showed no newer revision. [`ma` Go's findings](../../go/cmd/ma/README.md#known-gaps) explain why dataclasses cannot provide both method calls and first-class function attributes there, and why imports fail. Upstreaming a real upgrade is more than changing the pin: update the Rust FFI and conversions to the current snapshots, module/function values, name/import/OS suspensions and limits; add tests and rebuild every target binary. Even then `ma` must run the FFI in a child process. A pure-Go `monty-proto` client could instead be contributed without making `ma` wait for an FFI release. No new FFI build or upstream commitment verified.

[QuickJS-NG v0.18.0](https://github.com/quickjs-ng/quickjs/releases/tag/v0.18.0) is the active MIT fork, released November 1; it ships native CLI files, a WASI command and a WASI reactor. That is a usable prompt precedent, not proof of `ma`'s limits or process boundary.

**Shared artifact design.** Compile one pinned NG source revision with a small `ma` C shim, rather than adopting the upstream CLI or the reactor ABI as the product API. Expose bounded request/response buffers, explicit init/eval/pump/resume/free and a minimal import list. With an unchanged synchronous script calling convention, an imported host function can send one framed tool request and block the *worker* reading the reply; the agent remains free to await I/O. This does not need Asyncify or JSPI, but requires a reliable paused watchdog and no re-entrancy. With a changed `await` contract, the shim instead returns a promise and yields to a bounded job pump that resumes on the reply; make implicit parallelism, ordering and outstanding-call cancellation explicit. Plain core Wasm [JS imports are synchronous](https://webassembly.github.io/spec/js-api/index.html); returning a Node `Promise` is not a portable suspension mechanism. Use one object argument with `null`/missing defined as omitted; no host-object reflection or arbitrary JS references across IPC.

Use [Wasmtime 51.0.0](https://crates.io/api/v1/crates/wasmtime/51.0.0) in Rust, [`wasmtime` 51.0.0](https://pypi.org/project/wasmtime/51.0.0/) in Python (both November 20, Apache-2.0 with LLVM exception; Python packages native wheels), [wazero v1.12.0](https://github.com/tetratelabs/wazero/releases/tag/v1.12.0) in Go (May 29, [Apache-2.0](https://pkg.go.dev/github.com/tetratelabs/wazero), pure Go), and Node's built-in [WebAssembly API](https://webassembly.github.io/spec/js-api/index.html) in TypeScript (Node v26.13.1 available for this spike; [release index](https://nodejs.org/dist/index.json)). No per-host QuickJS build once the guest module is built. Rust/Python can use Wasmtime [fuel or epoch interruption](https://docs.wasmtime.dev/examples-interrupting-wasm.html); Go has [`WithMemoryLimitPages` and `WithCloseOnContextDone`](https://pkg.go.dev/github.com/tetratelabs/wazero#RuntimeConfig); Node needs an external process watchdog around blocking Wasm. Those are backstops, not equivalent VM budgets. For parity, use a guest memory maximum plus a shared interpreter allocator that records refusals as terminal; linear memory may need headroom for guest stack/ABI data if 256 MiB means interpreter allocations. [NG's C API](https://quickjs-ng.github.io/quickjs/developer-guide/intro) has `JS_SetMemoryLimit`, cooperative `JS_SetInterruptHandler` and byte-based `JS_SetMaxStackSize`, **not** exactly 200 language frames. Add a shared frame counter or explicitly change the recursion contract to a shared stack budget; for terminal limit failures latch the cause in the trusted shim/worker and suppress any successful result. Use a process kill backstop even when an engine poll would normally work. Qualify `Date` (including constructors and `Intl` if present), timer/OS/module APIs and entropy, not just file mounts; never register QuickJS `std`/`os` modules in the sandbox. [Node's WASI docs](https://nodejs.org/api/wasi.html) explicitly do not promise secure filesystem sandboxing.

Cache compiled modules in a prewarmed *process* and instantiate fresh guests, or accept compile/instantiate cost in each single-use worker. Each tool call pays both a guest/host copy and IPC. A shared native NG worker using the same product shim would avoid four WASM host adapters and probably be easier to package initially, but is one executable **per target**, not one byte-identical artifact, and misses the linear-memory boundary. No timing for either production shape was measured. The Go binding result below is not evidence for the performance or correctness of either shape.

## Starlark

The [language spec](https://github.com/bazelbuild/starlark/blob/master/spec.md) describes a deterministic Python-like configuration language, with keyword and positional calls and no unbounded loops or recursion in the standard dialect. It also has no script `try/except`: a failing host builtin normally aborts evaluation. Returning an error record instead would be a product change, as would teaching scripts to avoid Python imports and use `load` only when the host permits it. A builtin can be synchronous to Starlark while the worker waits on IPC; there is no common suspend/resume protocol across bindings.

One native Go or Rust Starlark sidecar for all four would remove dialect and binding differences, with the same framed IPC cost as Monty. It would still need stronger allocator control (or a shared WASM shim and linear cap), polling/kill for long builtins, and a replacement for catchable nested errors. Output and 500 calls remain host checks. No startup or parity run was measured. This is a reasonable configuration language, but a worse fit for the current tool scripts.

## Lua

[PUC Lua 5.5.1](https://www.lua.org/news.html) (August 3, 2026, [MIT](https://www.lua.org/license.html)) is a small C interpreter with exceptions (`pcall`), first-class functions and coroutines. Use named keys in `tools.read{path='x'}` as the keyword equivalent; `nil` removes a table key. Define deliberately how `nil`, arrays versus records, one-based indexes and multi-return map to structured tool data. A C callback can block on agent IPC, or a coroutine can yield and resume through the [continuation API](https://www.lua.org/manual/5.5/manual.html#4.5) rather than trying to return through an arbitrary C stack. These are different choices from a four-binding mix.

For parity, compile **one PUC Lua WASM module** with the same runtime choices as for QuickJS, or one native worker per target. Use only selected standard functions (no `io`, `os`, `package`, `debug`, native loading, or file-backed `load`); supply only the necessary imports, print sink and tool bridge. The [C API](https://www.lua.org/manual/5.5/manual.html) provides a custom allocator (`lua_newstate`) and instruction-count hooks (`lua_sethook`). A hook is not a hard wall deadline and need not run during native builtins; errors can be caught, so latch quota failure and use an external watchdog. Count guest-call depth explicitly across coroutines or change the 200-frame rule; constrain native/WASM stacks independently. A common interpreter and shim would make behavior substantially easier to align than these bindings, but guest/host copy, IPC, compile/instantiation and fresh worker costs remain. No Lua startup numbers measured. This is feasible but offers less reason to migrate scripts and prompts than JavaScript does.

- **Purpose-built code mode:** [Cloudflare Agents' codemode package](https://github.com/cloudflare/agents/tree/main/packages/codemode) describes TypeScript/JavaScript and a Dynamic Workers executor with tool bindings. Good API prior art, not a standalone local interpreter dependency with identical deployment in these four CLIs. Pi is the closer precedent; its contract also differs. [Extism v1.41.0](https://github.com/extism/extism/releases/tag/v1.41.0) (October 9, BSD-3-Clause runtime) is a [WASM host-function ABI](https://extism.org/docs/concepts/host-functions/), not the scripting language and supervisor; adding it would not settle the engine or metering choices.

## Comparison

| Candidate | Same interpreter in all four? | Fits current script contract? | Main work or reason not to choose |
|---|---|---|---|
| Monty 1.6.0 native worker | Yes, same pinned build/profile per target | Yes | Go protocol client and packaging, common policy and conformance |
| Monty component/core WASM | Yes if we build a shared core adapter | Yes in principle | Component ABI or new shim, WASM hosts, process watchdog; no Go path tested |
| New `gomonty` FFI | Only after a large port and matching pins | Not in latest release | Release cadence, native ABI and conversion drift, still child process |
| QuickJS-NG single WASM module | Yes, same bytes plus pinned shim | JS change; choose sync or `await`, result and recursion semantics | Hardened imports/ABI, allocator, frame count, limits and four host runners |
| Separate QuickJS bindings | Not by default | Same JS only in broad outline | Fork/version and wrapper semantics, timeout and callback gaps |
| Starlark sidecar | Yes if one implementation; not with four bindings | No catchable tool errors; narrower language | Memory accounting and dialect/API changes |
| Lua sidecar or one WASM module | Yes with one implementation/artifact | New syntax, value and result contract | Memory/hooks/stack profile and prompt changes |

## Throwaway checks

Ran outside the checkout under `$HOME/.cache/ma-std-tmp/codemode-spikes/` on Linux x86-64 with Go 1.27.4 and `CGO_ENABLED=0`. Worker artifacts had separate download directories, and the test harnesses ran with a cleared environment and network unshared (`bwrap`). Timings are wall time on one machine, not service benchmarks.

- **Go → Monty 1.6.0 native worker.** Extracted the PyPI manylinux x86-64 worker, verified the wheel SHA-256 against PyPI, used the protocol-8 schema and a minimal Go wire encoder/decoder. In 25 single-use processes, spawn + configure/feed of `'ok'` + kill/reap was **0.68 ms p50, 1.17 ms p95**. `import tools; f = tools.read` followed by `f(path='in.txt')` produced a keyword call, awaited a mock completing after **75.19 ms**, printed `whitby` and returned `WHITBY` (**76.44 ms** total with a **50 ms** compute-turn limit). The reference-style allocation loop with a **256 MiB** cap reported `MemoryError` at **268,691,745 > 268,435,456 bytes** in **73.99 ms**. A loop hit the **50 ms** turn limit in **51.48 ms**; a separate run was killed/reaped at **75.50 ms** by the parent and reported EOF with `signal: killed`. Next fresh run returned `still here`. This verifies the core compatibility claim, not a production decoder, OS policy, tool validation, mid-tool cancellation or cross-platform distribution.
- **Go → `fastschema/qjs` v0.0.6 → wazero v1.9.0.** Mounted an empty directory. A sync JS callback waited on a Go goroutine returning a mock value and evaluated to `WHITBY` in **18.78 ms** (15 ms mock wait). Cold instantiate/eval/close including Wasm compilation was **292 ms**; 24 fresh warm runtimes sharing compilation had **2.63 ms p50, 3.02 ms p95**. With `MemoryLimit=32 MiB`, a loop retaining 20,000 separately allocated and filled 10,000-byte `Uint8Array`s returned `finished`; the option did not stop that workload. This is not a claim about why it passed or what the upstream C API would do. A **50 ms** wazero context cancellation terminated a busy loop, but wrapper calls and cleanup panicked after module closure (**53.61 ms** total; harness recovered). A fresh instance had no script state. Neither limit observation qualifies this binding for `ma` unmodified.
- **Official QuickJS-NG reactor inspection.** Verified the release digest and read imports/exports with Node. The **1,560,132-byte** module exports eval, C callback registration, memory and interrupt setters, but imports **22 Preview 1 functions**, including clock, file/path and process-exit functions. This confirms an ABI/capability adaptation is required (or a rebuild with fewer imports), not that the VM exposes each import to JS. No end-to-end custom QuickJS module with enforced limits was built.

## Recommendation and changes

1. **Keep Monty Python; ship the same pinned Monty 1.6.0 native worker for all four builds.** This fixes the observed Go gaps without changing model scripts, and the Go spike covered suspension, timeout, allocation failure and recovery. In the Tools section, keep Python, positional/keyword/`None`, `RuntimeError`, `describe_tool` and `search_tools`, and last-expression output. Clarify that `tools` is both prebound and importable and its functions can be assigned; specify the shared clock/OS policy, allocation metric, terminal failures and canonical value rendering. In `codemode-nested`, exercise direct call, import, alias and structured/positional arguments without exposing nested results to the model. Keep the Python `sandbox-memory` load and `MemoryError`/recovery expectation; add a caught-limit test. **Go:** replace `gomonty` and the interpreter re-exec with a bounded protocol-8 client supervising the sidecar. **Rust:** retain `monty-pool` but use the common worker path and isolation/limit profile. **TypeScript and Python:** retain the current native Monty clients if they can select and supervise the same worker on each target, otherwise use the shared worker protocol directly; no browser worker in the agent. Check the version, package provenance and worker digest per target in CI. Test the same frames and same model transcript across all four; do not downgrade the contract to match old Go.
2. **If changing the script language is worth it, use JavaScript on one custom QuickJS-NG WASM module.** Go, Rust, Python and Node load the same checked digest with the hosts described above, each in a child. In Tools, specify strict JavaScript in an async function body, `await tools.name({field: value})`, `null`/missing omission, tool failures rejecting with `Error`, `print` and explicit `return` instead of the last expression. Keep the names `describe_tool`/`search_tools` for discoverability; index and prompt list schemas as named objects. Prefer sequential awaited calls initially; define ordering and cancellation and explicitly disallow concurrent outstanding calls if not implemented. Specify the exact recursion and memory metric rather than implying `JS_SetMaxStackSize` is 200 frames. Change `codemode-nested` to use awaited object-argument calls and check print plus return. Change `sandbox-memory` to bounded distinct allocations and require one host-normalized memory error and a good next run even if the script tries to catch the failure. **Rust:** new Wasmtime runner and process supervision in `tools-code`. **Go:** replace the Monty worker with wazero configured for the one module. **TypeScript:** replace Monty with a Node child hosting core Wasm, not `worker_threads` or default WASI. **Python:** replace Monty with a child hosting Wasmtime. Do not migrate until the same shim passes the limits and boundary suite on all four.

For either option, run the [reference kit](../../conformance/reference/README.md) unchanged *across* the four builds after updating its common fixtures; compare normalized nested tool traces, `codemode` result bytes, error classifications, truncation and prompt schemas (not timings or OS paths). Add cases for omitted arguments, discovery/count boundaries 500/501, time while computing versus while waiting, recursion 200/201 or its documented replacement, print bytes and UTF-8, malformed/oversized frames, denied ambient APIs, cancellation while awaiting a tool, and crash then fresh recovery. Run on every supported target; verify that outputs depend on the shared profile rather than host JSON/error defaults. The two existing fixtures alone cannot establish parity.

**Not verified:** full four-build or cross-platform parity, the production Go decoder and packaging, a Go Monty WASM host, a shared QuickJS/Lua WASM adapter with terminal allocator limits and exact recursion, or model fluency by benchmark. No claim that any wrapper's defaults meet the Tools contract.
