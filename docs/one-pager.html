Modular Agent

An AI agent made of a small Harness and swappable plugins, written down as contracts, and proven by five independent builds in five languages that run each other's parts.

Why

The problem

  • Most agents are one program. The loop, model access, tools, history and safety checks are tangled together, so you can't study or replace one part without the rest.
  • Making an agent survive a crash, run its tools somewhere else, or be driven by another system usually means rewriting it.
  • Extensions written for one agent only work in that agent, in its language.

The question

Can an agent be described precisely enough, as what each part does rather than how, that independent teams in different languages build parts which plug into each other and keep their promises, even through a crash?

It is a research project: understanding how an agent fits together. Production performance is not a goal.

How

DescribeParts, contracts and guarantees: what passes between parts, never the wiring (ADR 0010).
Build clean-roomIndependent builders get only the documents, and log every gap they had to decide.
Bind the wireSmall versioned bindings: ACP for hosts, plugins in any language, shared data, history over HTTP.
CheckA conformance kit per binding: plugin kit (110 checks), ACP kit (109), portable sessions (86).
SwapEvery build's agent with every build's parts, through a real kill -9. Each failure becomes a rule and a kit check.

What we learned

Each build passed every kit on its own, yet every round of swaps found holes the kits missed: 24 across rounds two to five. Nearly all were the same kind: a receiver relying on a value the binding never defined, such as a timeout of 0, an event name, the names of rights, or a folder replaced on restore.
The descriptions of the parts held throughout. What kept needing work was the exact values one side relies on from the other. So the recipe is: describe the parts, bind each wire narrowly, write a kit per binding, and run every pairing.

Status

Done: 19 decision records; five builds passing every kit and every 5×5 swap matrix; ACP /2, several actors, jobs, rewinding and remote output gates.

In progress (round six): listing proposed input, a shared shape for output events, tenant and administrator limits on authority, and one plugin per name.
