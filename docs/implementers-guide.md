# Implementer's guide

Start here if you are building an agent from [production edition 3](adr/0021-production-edition.md). The example traces a single approved file read from the ACP client to the working environment and back. It shows where to look up each decision. It does not set requirements.

## How to read the specification

[Conformance](conformance.md#the-documents) tells you which documents set requirements. [Contracts](contracts.md#rules-every-implementation-follows) owns core behavior, including when work can start and what survives interruption. [Security](security.md#trust-boundaries) owns the trust boundaries. Each [binding](bindings/README.md) owns its wire: [ACP](bindings/acp.md) for the client and agent, [Plugin](bindings/plugin.md) for the Harness and child plugins, [History HTTP](bindings/history-http.md) for the history client and service, and [Shared data](bindings/data.md) for common JSON and portable sessions.

The capitalized [keywords](conformance.md#keywords) distinguish absolute requirements, recommendations that need a documented reason for departing from them, and options with fallbacks. This guide, [Architecture](architecture.md), [Scenarios](scenarios.md), [past decisions](adr/README.md) and kit results help you read the rules. They do not override them. If two applicable rules disagree, [report a defect](conformance.md#reporting-a-defect) rather than choosing the behavior that happens to pass a test.

A core agent can have local history and no wire profiles. The optional claims add the ACP agent or client role, the plugin host or served plugin role, and the history HTTP client or service role. Start with the [role and kit table](conformance.md#what-conforms). Record the [specification revision and binding versions](conformance.md#versioning) you accept. ACP agents speak both binding versions over ACP v1. [Portable sessions](bindings/data.md#portable-sessions) are a separate claim about the records, not a consequence of using HTTP history. Read the [session declaration](bindings/acp.md#the-declaration) for options such as continuation after restart, late answers to questions and rewind. Those answers are not late model responses; [Provider coverage](bindings/plugin.md#the-host-asks-a-provider) describes the request and response profile. A production deployment chooses its own [operator policy](security.md#what-an-operator-configures). No combination of binding claims supplies that policy.

## One turn, end to end

The user sends “Read `harbour.txt` and tell me the harbour it names.” The file contains `Whitby`. This example uses an idle, already kept session, a local Runtime, an in-process stateless Provider that does not run tools, a trusted `read` tool, and the session's own working environment. An approval plugin is loaded and the recorded policy is `all`. The prompting actor has `input`, `tools`, `approve` and `watch`, and is present on the ACP connection. The deployment allows the file's content to go to this Provider. This session does not offer steering. No context-management handler changes the default view.

1. **Admit input.** The ACP Interface takes the actor from the authenticated connection. The client sends `session/prompt` with a fresh key. The Harness checks project, tenant and authority, reserves the key in the admission path, and runs the input transform. Here it passes the text through. The Harness commits `inputAccepted` as the admission, not as a message to the model. If the client retries the same key, it is asking about that admission, not starting this sequence again. For keys, receipts and what the waiting prompt returns, see [ACP input admission](bindings/acp.md#input-admission), [Prompts](bindings/acp.md#prompts) and [core Input](contracts.md#input).
2. **Start the turn.** The Harness gathers the before-turn contributions. It records `turnStart` with the selected model, settings, prompt and context additions, tool offer and attribution. It commits the first `input` with it, in that order, before invoking the Runtime. This `input` is the user message the turn actually took. The Runtime's `turn.start` hook observes the start. See [Settings](contracts.md#settings), [Hook points](contracts.md#hook-points) and [Recording order and ownership](bindings/data.md#recording-order-and-ownership).
3. **Prepare the first step.** The Runtime uses the default model view: the current branch's model-visible messages with the specified context projection. The starting request uses that view, the prompt, the tools and the turn's settings. The step hook can transform the prepared request. The Provider request hook acts before inference. Preparation here does not add a history entry of its own. The durable dispatch checkpoint is the next record. See [Hook execution](contracts.md#hook-execution), [Context and interrupted work](bindings/data.md#context-and-interrupted-work) and [Provider state](contracts.md#provider-state).
4. **Make the model attempt.** The Harness applies the Provider request transform and commits `modelRequest` for the fresh step id before the local Provider starts inference. The record captures the model, the final tool offer and the repeat-safety decision. The rules on that record determine whether it also holds the exact request for recovery. It is not a message to the model. The Provider streams pieces and answers with a request for `read` on `harbour.txt`. A live piece is not the settled response. The Runtime commits the `response` linked to that attempt before an agent-run call from it can start. See [Recovery and repeating work](contracts.md#recovery-and-repeating-work), [Recording order and ownership](bindings/data.md#recording-order-and-ownership) and [Call identities](bindings/data.md#call-identities-and-mappings).
5. **Gate and ask.** The Runtime invokes `tool.before`; the Harness enforces the gate decision at dispatch. In this example the input stays unchanged and the approval handler asks. The Harness commits `inputRequest` bound to the call and its registration before the Interface offers a gated `session/request_permission` showing the exact call. The actor chooses `allow`. The Harness checks the actor's current eligibility and commits the winning decision as `inputAnswer`. Neither question nor answer is a model message. See [Gates and registration](contracts.md#gates-and-registration) for changed inputs and invalidated decisions, [Approval policy](contracts.md#approval-policy), [ACP Approvals](bindings/acp.md#approvals) and [ACP Questions](bindings/acp.md#questions) for competing answer routes.
6. **Dispatch and execute.** Approval is not the handoff. The Harness owns the final dispatch check, including the rights behind the work, the final recorded tool offer and the unused decision for this call. The Harness commits `toolStarted` before handing the call to the tool source. The record does not replace the final check at handoff. The source reads the file in the session's working environment, not through the ACP client's file methods. In this example the environment confines file reads to the project. Progress, if any, is live; the start record is the checkpoint. See [Tool dispatch](contracts.md#tool-dispatch), [Working environment](contracts.md#the-working-environment) and [ACP initialization](bindings/acp.md#initialize).
7. **Settle the call and the step.** The tool returns its result with `Whitby`. The Runtime runs `tool.after` on that result and commits the checked `toolResult`. The status describes what happened; the result hook works on content and value. Now the Runtime runs `step.after`, after the call round, not between the model response and the tool. The result is already in history at that boundary. See [Settlement](contracts.md#settlement), [Recovery and repeating work](contracts.md#recovery-and-repeating-work) and [Hook execution](contracts.md#hook-execution).
8. **Make the second attempt.** At the next step the view includes the assistant call and its tool result. The Runtime prepares the request and the Harness commits a new `modelRequest` with a fresh step id before inference. The Runtime records the answer, “The harbour is Whitby,” as the second `response`. This time the call round is empty. The Runtime runs `step.after` for that answered step and reaches the [turn result and end hooks](contracts.md#hook-points). The Harness commits `turnEnd`, with the result, outcome and usage. If the turn instead required a shaped result and `turn.result` refused it, the Harness would first record `resultFeedback`. The next prepared request for that turn would carry the reason as an extra user message, not as a new admitted input. See [Context and interrupted work](bindings/data.md#context-and-interrupted-work), [Standard kinds](bindings/data.md#standard-kinds) and [Identities and usage](contracts.md#identities-and-usage).
9. **Deliver each view.** Delivery happens throughout the turn, not just at the end. The ACP client sees authorized, gated call notices, progress, terminal updates and model chunks. Only a present eligible answerer with a deliverable exact approval view gets that route to answer. A connection with `watch` but no `approve` can see its own authorized updates, not act on the approval. The prompting actor gets the gated settlement in the prompt reply after the final updates. The client reads the outcome rather than inferring it from the stop reason; see [Prompts](bindings/acp.md#prompts). The model sees the internal request view from step preparation, not ACP updates or the approval exchange. An authorized plugin's raw read is a separate path, not the client history projection. See [The output gate](contracts.md#the-output-gate), [ACP Output gate](bindings/acp.md#output-gate), [ACP Entry](bindings/acp.md#entry) and [plugin read scope](bindings/plugin.md#authority). A withheld reply is not a rollback; the ACP gate section explains how clients reconcile it.

The entries below are in kept order for this example. All belong to one session. `i1` is the admission, `t1` the turn, `s1` and `s2` the attempts, `c1` the call and `q1` the approval. These are labels, not a wire fixture. Use [Standard kinds](bindings/data.md#standard-kinds) for fields, owners and visibility.

| Entries in kept order | Matching work |
|---|---|
| `inputAccepted` | `i1`, the keyed admission |
| `turnStart`, `input` (one batch) | `t1`, taking `i1` |
| `modelRequest`, `response` | `t1`, `s1`; the response proposes `c1` |
| `inputRequest`, `inputAnswer` | `t1`, `s1`, `c1`, `q1`; an exact approval and its answer |
| `toolStarted`, `toolResult` | `t1`, `s1`, `c1`; dispatch checkpoint then settlement |
| `modular-agent.stepAfter` | `t1`, `s1`; recorded gate decision |
| `modelRequest`, `response` | `t1`, `s2`; final text, no calls |
| `modular-agent.stepAfter` | `t1`, `s2`; recorded gate decision |
| `turnEnd` | `t1`, completed, no open calls |

## The same turn with a remote Runtime

Only the Runtime moves to another process in this example. The ACP Interface, store client and approval handler remain on the Harness side. After the [handshake](bindings/plugin.md#starting-the-handshake), the turn uses one `runtime/runTurn` parent. The [transport](bindings/plugin.md#transport) defines its lifetime; the [callback table](bindings/plugin.md#runtime-callbacks) and [authority table](bindings/plugin.md#authority) say what the child can ask under it. Read down the two columns together.

| Harness, as plugin host | Remote Runtime |
|---|---|
| Admits the ACP prompt, runs `turn.before`, commits the turn and taken input, then sends `runtime/runTurn`. See [The host asks the Runtime](bindings/plugin.md#the-host-asks-the-runtime). | Receives the pinned turn. Invokes `turn.start` through `host/runtime/hook`. Reads needed history with `host/history`, not from ACP replay. |
| Allocates the step id on request and returns the prepared request, applying `step.before` at preparation. | Calls `host/runtime/newId` and `host/runtime/prepareStep`. This session has steering disabled. See [Model attempt sequences](bindings/plugin.md#model-attempt-sequences) for the full callback order. |
| On `host/runtime/model`, commits the effective `modelRequest` before calling the Provider, with the Provider transform already applied. It forwards the model pieces and answer. The host emits the standard model events. See [Runtime records and effects](bindings/plugin.md#runtime-records-and-effects) and [Turn events](bindings/plugin.md#turn-events). | Requests inference for the allocated step and submits the returned assistant message through `host/runtime/record` as the `response`. The host validates it and supplies the record metadata. |
| Validates the committed call and runs the `tool.before` chain. Its local approval plugin asks through ACP; the host records the question and answer and tracks the exact allowance. A refusal would carry the result the host had already committed. See [Runtime records and effects](bindings/plugin.md#runtime-records-and-effects). | Asks for `tool.before` on `c1`. Uses the allowed call returned by the host. On refusal it would use the supplied result, not construct one. |
| On `host/runtime/runToolCall`, checks dispatch, commits `toolStarted` and invokes the tool in the session's environment. It runs `tool.after` and commits the result before replying. | Asks to run the allowed call. It does not run the tool or call the environment as a Runtime. A later acknowledgement uses the committed result unchanged, not a second write. |
| Enforces the step boundary and prepares and dispatches the second attempt under the same checks. See [Model attempt sequences](bindings/plugin.md#model-attempt-sequences). | Invokes `step.after` after settlement, takes the next step with a fresh id, records the answer and invokes `step.after` for the empty call round. |
| If `turn.result` refuses a shaped result, records `resultFeedback` before returning the refusal and adds the recorded reason to the next `host/runtime/prepareStep` reply. See [Hook execution](contracts.md#hook-execution). | If retrying, requests a new step id and calls `host/runtime/prepareStep`; it does not add a second feedback message. |
| Runs the end observation on the effective outcome, validates the reply and commits `turnEnd`. It owns standard events and gated ACP delivery, including the prompt reply. See [Runtime callbacks](bindings/plugin.md#runtime-callbacks) and [Turn events](bindings/plugin.md#turn-events). | Invokes `turn.end` as its last callback and answers the parent. The callback is an observation before commit, not a way to write `turnEnd`. |

**If the Provider is remote too.** The Runtime still asks `host/runtime/model`. The host sends `provider/request` for preparation. The Provider calls `host/hook` for `provider.request` and waits. The host transforms the request at that callback and commits the final `modelRequest` before returning the payload. The Provider uses that answer for inference. This is the checkpoint even if there are no transform handlers. Its tool list, not the list prepared by the Runtime, proves which tools were offered. Before returning the message, the Provider sends it through the [four-field response callback](bindings/plugin.md#the-host-asks-a-provider).

## When things go wrong

**The process is killed mid-tool.** With a surviving store, compare the committed `toolStarted` with the absence of a terminal `toolResult`. A transient Runtime ends the interrupted turn as failed. For durable recovery, the host settles calls that cannot safely run before handing off. An unsafe started call with no confirmed outcome settles as `outcomeUnknown` and stays out of `interrupted.calls`. With no surviving history there is no turn to reopen. See [Recovery and repeating work](contracts.md#recovery-and-repeating-work) and [Working environment](contracts.md#the-working-environment).

**The interrupted turn had an answered step.** In `runtime/resumeTurn` the host identifies the last answered step and returns the gate decision if it committed. The Runtime reuses it. When the checkpoint proves there is no decision, the Runtime asks for `step.after` once, after the calls have their recorded dispositions. A checkpoint that cannot distinguish the two cases fails the turn. Read [the resume request](bindings/plugin.md#the-host-asks-the-runtime) and [what the history records](bindings/data.md#recording-order-and-ownership).

**The user cancels.** `session/cancel` targets the session's running turn. Cancelling the `session/prompt` RPC only stops waiting for its reply. If turn cancellation wins, the Harness stops new dispatch, closes affected questions, settles calls according to what it can confirm, and hands back untaken input at the cutoff. Turn cancellation and session close have different job scopes. See [ACP Cancelling](bindings/acp.md#cancelling), [Settlement](contracts.md#settlement) and [Jobs](contracts.md#jobs).

**A question outlasts its turn.** This is a declared path for a qualifying non-approval question, not for the approval in this walk-through. At the end of the wait the invocation relinquishes execution and the Harness records the pending disposition. After `turnEnd`, closure of all the originating turn's open questions makes one continuation eligible. The answer supplies a decision, not a tool result; the call runs through current checks. The [question rules](contracts.md#questions) define safe effects before a question, when the continuation starts, and the separate case of a process stop during an in-turn wait. See [ACP Questions](bindings/acp.md#questions) for how the client finds and answers it.

**The history lease is lost.** Writer uncertainty stops new effects, not just history writes. The Harness requests cancellation of running calls and leaves the session interrupted. An ambiguous append is not permission to dispatch or to reuse a stale lease. On reopen the agent reconciles against the committed record. The [history lease rules](bindings/history-http.md#writing-one-writer-at-a-time) define renewal, the cutoff and safe resend; [Recovery](contracts.md#recovery-and-repeating-work) defines what the Harness does when a commit or lease is uncertain.

**A plugin process dies.** The plugin host identifies the lost part and settles unanswered RPCs. The error describes the connection, not whether an external action ran. A tool call already sent without a confirmed outcome is different from one never sent. A lost gate does not allow an effect, a lost Runtime is not silently replaced, and a job does not become finished because its owner disconnected. See [Connection loss](bindings/plugin.md#errors-and-connection-loss), [Parts that are lost](contracts.md#parts-that-are-lost) and [Jobs](contracts.md#jobs).

**Another build reopens the session.** Set the same [ACP connection actor id](bindings/acp.md#starting) on both builds when testing a keyed retry for the same principal. Use an authorized project and tenant. The reopener acquires the lease, folds session state in kept order, then uses the branch to reconstruct model context and find recovery candidates. Recorded rights still govern, including a departure. The new build does not inherit credentials, Provider state or project points from portable records. It does not substitute a model for one it cannot offer. Opening does not wait for recovered work or an answer. See [Portable sessions](bindings/data.md#portable-sessions), [Authority](contracts.md#authority) and [ACP Sessions](bindings/acp.md#sessions).

**The user rewinds with a remote working environment.** The host checks every later saved point for the session with `env/checkPoint` before touching the project or starting the journal. One missing or unverifiable point stops the rewind. A point can still disappear between the check and restore. If restore then returns `not_found`, the host follows the journal's rollback path. See [Paths and points](bindings/plugin.md#paths-and-points) and [Rewinding](bindings/data.md#rewinding).

## A build plan

Use disposable processes, workspaces, credentials and stores. The kits use a fresh `HOME`; use launchers that can find their tools without per-user setup. Start with your own core tests before claiming any binding. At every later milestone, keep the earlier checks green and add the applicable kit checks. The [kit table](conformance.md#the-conformance-kits) gives the commands and distinguishes fixture coverage from conformance.

1. **Local Harness, Runtime and fake Provider.** Drive the example without ACP first. Capture the record and the two model requests. Swap in a fake history writer or gate that fails at dispatch. Useful exit checks are commit order, no effect after a failed commit, and a response and result paired with the right attempt and call. This is the local test suite; there is no standalone core kit. Use [Recovery](contracts.md#recovery-and-repeating-work) and [Hook execution](contracts.md#hook-execution) as the oracle.
2. **History and recovery.** Add durable appends, checkpoints and a reopener. Exercise transient and durable behavior with a committed result, a started but unsettled call, and a known unstarted call. Test both sides of the `step.after` commit. End with recovery tests at those boundaries and the [history kit](../conformance/history/README.md) passing if you serve HTTP, including the restart check on a disposable store. Add the ACP crash checks once the Interface is available.
3. **ACP.** Add negotiation, session open and replay, prompt admission, keyed retry, the approval exchange and cancellation. Test a blocked approval view as well as the happy path. End with the [ACP kit](../conformance/acp/README.md) passing for both versions, including `--crash-checks` against a kept store for the recovery paths you claim. The [conformance fixture](bindings/acp.md#conformance-mode) gives you a scripted version of the file read using `tool:read {"path":"harbour.txt"}`, without relying on a real model to choose the call.
4. **Plugin binding as host.** Add registration, parent-scoped callbacks and the host-owned checkpoints. Use another build's fixture, including its Runtime if you claim that role. End with ACP `--plugin-checks` and `--probe-checks` passing where applicable. Compare the local and remote turn records, not only the final text. See [Runtime records and effects](bindings/plugin.md#runtime-records-and-effects).
5. **Plugin binding as plugin.** Serve the fixture roles and any Runtime tiers you offer. End with the [plugin kit](../conformance/plugin/README.md) passing with the kit as host, then swap with another ACP-driven agent. A pass as a plugin does not test your host side.
6. **Portable sessions.** Reopen standard history with a second build on a disposable shared service. Include interrupted attempts, previously taken inputs, tombstones and a narrower or departed actor. End with ACP `--portable-checks` and `--then` runs in both directions, including `--crash-checks` for applicable restart paths. Add `--probe-checks` to cover remote Runtime attempt recovery; the normal portable run does not cover it. The [portable fold](bindings/data.md#portable-sessions), not either build's private state, is the comparison point.
7. **Several actors, tenants and limits.** Add representative identities, proposals and releases, and check revocation between approval and handoff. Cover bounded rights across reopen and a budget shared by concurrent sessions. End with the [ACP authorization and limit checks](../conformance/acp/README.md) passing for the supported features, plus local checks for deployment accounting and isolation the kit does not establish.
8. **Jobs, then rewind.** For jobs, finish with ACP `--job-checks` and cross-build recovery runs covering atomic report admission and exclusive resumption. For rewind, finish with the applicable ACP move checks and plugin point checks. Add failure tests around the [rewind journal](bindings/data.md#rewinding), including foreign points and interrupted restore or rollback.
9. **Production acceptance.** Do not postpone trust boundaries until this milestone.
